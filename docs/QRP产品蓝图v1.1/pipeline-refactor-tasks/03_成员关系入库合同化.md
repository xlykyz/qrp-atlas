# 任务提示词｜成员关系入库合同化

## 工作目标

将以下两条现有人工入库能力正式接入 PipelineContract，并保留其“显式范围、人工触发、历史关系数据”的业务边界：

- `industry_membership_ingest`
- `index_component_ingest`

两条任务均只完成源码合同化、离线测试和注册，不新增生产 schedule。

## 调查范围

重点调查：

- `src/qrp_atlas/pipeline/industry_membership/`
- `src/qrp_atlas/pipeline/index_component/`
- 对应 contracts、映射、CLI、服务层和测试
- `industry_membership_history`、`index_component_history` 的主键、有效日期和 PIT 字段
- `deploy/pipeline/pipeline-registry.json`
- Pipeline 正式开发规则及现有正式 Contract 范式

先确认两类成员关系的来源接口、日期范围、证券或指数范围、历史修订和重复记录语义。不得把“append-only”简单等同于允许重复写入。

## 必须完成

1. 为两个稳定 ID 分别建立正式 `PipelineContract`；可以共享有限的 Tushare 调用或写入辅助能力，但不得创建脱离当前需求的通用入库框架。
2. 将现有 CLI 参数整理为明确的 `ParameterContract`，包括日期、行业/指数范围、代码或批次等真实参数；未知或历史 wrapper 才提供的参数不得猜测。
3. 设置 `manual_execution_allowed=true`，不设置生产 schedule，不把人工操作伪装成每日任务。
4. 明确输入来源、返回结构、目标范围完整性和空结果语义；当 provider 无法证明全量覆盖时，必须保留边界说明。
5. 明确历史关系表的业务唯一键、有效时间、来源时间、修订或覆盖策略，以及同一参数重复运行的幂等结果。
6. 写 `quant.db` 时使用 `quant_db_writer`；读取已有历史或基础表时使用准确的 `resource_reads`。
7. 明确事务边界。批次中途失败不得留下被视为完整范围的半成品；如果现有业务确实是逐批 append，则必须有可审计的完成条件和恢复策略。
8. 将同一 `ExecutionControl` 传入 provider、分页/批次循环和写事务，取消后不得继续请求下一范围或开始新事务。
9. 输出标准 `PipelineResult`，分别报告请求、批次、读取、写入、涉及资产/行业/指数数量和数据库耗时。
10. 验收通过后加入 source catalog，并更新注册表状态、完成标记、幂等和参数证据。

## 测试要求

至少覆盖：

- 两条 Contract 的注册、描述、人工执行权限和参数解析；
- 单范围、多范围、空范围和非法范围；
- 同一参数重复执行、历史已存在、provider 重复记录；
- 缺字段、错误日期、部分返回、分页失败和网络异常；
- append / upsert / replace 的真实行为与表契约一致；
- 事务失败或取消后不产生伪完整结果；
- deadline 在请求前、批次中和写入前生效；
- 输出行数与指标一致；
- 现有六条市场 Contract 和前序已完成 Contract 不回归。

全部测试使用 mock Tushare 和临时 DuckDB。

## 边界

- 不新增自动调度，不修改 Hermes 或 deploy 启用配置。
- 不修改表主键、PIT 时间语义或历史保留规则，除非现有实现与已封板 contracts 直接冲突。
- 不把行业成员和指数成分强行合并为一个 Contract。
- 不顺手改造 fundamentals、earnings forecast、PIT backfill 或 System B。
- 不建设通用数据湖、版本管理平台或复杂断点续传系统。

## 完成后汇报

分别汇报两个数据域的参数、唯一键、PIT/历史语义、写入与恢复方式、共享代码范围、测试结果、修改文件、注册表变化和仍未解决事实。不得部署或合并目标分支。
