# 任务提示词｜个股研究报告合同化

## 工作目标

将以下两条个股研究报告能力正式接入 PipelineContract：

- `research_stock_morning`
- `research_stock_evening`

现有注册表将其描述为确定性 Python Pipeline，但历史 Hermes wrapper、动态日期参数、输入输出、完成标记、幂等和 Agent 依赖仍有未解决事实。本任务必须先澄清真实业务链路，再做最小合同化。

## 调查范围

重点调查：

- `src/qrp_atlas/pipeline/research_report/`
- 相关研究表 contracts、报告文件格式、CLI、service 和 tests
- 仓库内可审计的 `research_stock_daily` 历史 wrapper 与文档
- `deploy/pipeline/pipeline-registry.json` 中 morning/evening 两条记录
- Pipeline 正式开发规则、结果日志和已有 Contract 模式

不得默认接受注册表中的 `external_hermes_agent` 为真实业务输入。必须区分确定性数据生产、报告渲染、消息发送和可选 LLM 解释；LLM 不能成为 Pipeline 成功条件。

## 必须完成

1. 确认 morning 与 evening 在输入截止时间、目标日期、输出内容、覆盖范围或完成语义上是否不同。默认保留两个稳定 ID，并允许共享底层研究计算与渲染代码。
2. 为两个 ID 建立正式 `PipelineContract`，由 `PipelineInvocation` 解析目标日期/时间窗口，消除 shell 动态日期对正式执行的依赖。
3. 列清真实输入表及 freshness。不得以模糊的“quant.db”作为输入声明，也不得把不参与确定性计算的 Hermes Agent 伪装成数据依赖。
4. 明确数据库输出、报告文件输出和任何投递动作的边界：
   - 业务成功必须由可验证的数据/文件 completion 决定；
   - 可选通知或解释失败不得伪造数据任务失败或成功；
   - 不属于 Pipeline 的投递能力应保持在边界外。
5. 明确同一目标日 morning/evening 的唯一键、覆盖/追加方式、报告重跑、历史保留和部分输出恢复。
6. 涉及 `quant.db` 写入时使用 `quant_db_writer`；只读表使用准确 `resource_reads`。报告文件写入必须采用明确 staging/atomic replace 或其他已证明安全的方式。
7. 将同一个 `ExecutionControl` 贯穿输入读取、批量研究计算、文件生成和写事务；取消后不得继续生成新报告或提交新事务。
8. 输出标准 `PipelineResult`，包括处理标的、读取/写入行数、报告文件、阶段耗时和 completion checks。
9. 建立代表性标的规模的本地性能基线，避免逐标的重复全表扫描；不得仅通过提高 timeout 掩盖明显退化。
10. 完整验收后加入 source catalog，并更新注册表中的真实依赖、完成标记、幂等、Agent 边界和性能证据。

## 测试要求

至少覆盖：

- morning/evening 的稳定注册和目标窗口差异；
- 输入表缺失、字段缺失、数据过期、无符合条件标的；
- 正常生成数据库结果和报告文件；
- 同一目标重跑不产生冲突有效版本或重复历史；
- 数据库成功但文件失败、文件成功但数据库失败等原子边界；
- 可选通知/解释不可用时不影响正式数据 completion；
- 取消/deadline 在读取前、计算中、文件提交前和数据库写入前生效；
- 指标、outputs 和实际文件/表行数一致；
- 现有正式 Contract 不回归。

测试不得访问生产数据库、真实消息渠道或真实 LLM。

## 边界

- 不重新设计个股研究算法、评分、内容模板或产品展示。
- 不把 Agent/LLM 接入 Pipeline 成功路径。
- 不建设通用报告平台、消息总线或通知中心。
- 不修改 Hermes cron 或生产 wrapper。
- 不触及行业研究、CNINFO、IRM、手动入库或 System B。
- 对历史 wrapper 与当前源码不一致之处，以当前可执行源码和已封板业务文档为依据；无法证明的事实保持 `UNRESOLVED`。

## 完成后汇报

汇报 morning/evening 的真实差异、确定性输入输出、Agent 与投递边界、完成/幂等/原子性、性能基线、测试结果、修改文件、注册表变化和未解决事实。不得部署或合并目标分支。
