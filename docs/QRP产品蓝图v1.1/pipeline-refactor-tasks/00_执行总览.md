# 既有 Pipeline 合同化重构｜执行总览

## 1. 当前基线

PR #51 已合并到 `develop/v1.1`，merge commit 为 `e8d422dca24eeacc7ab83c3ba74b6c30bdabe89a`。PipelineContract 正式门禁、Job Orchestration、数据库级写锁、终态 JobResult、ExecutionControl 和权威文档已经封板。

后续既有 Pipeline 重构继续**只在**长期分支 `feature/v1.1-pipeline-market-data-refactor` 上推进，不另建功能分支，不做生产部署，不切换 Hermes 调度权。

## 2. 本轮范围

本轮将尚未合同化的 13 条既有确定性能力拆为 6 个工作包：

| 序号 | 工作包 | Pipeline ID | 数量 |
| --- | --- | --- | ---: |
| 01 | CNINFO 采集 | `cninfo_main_update`、`cninfo_incremental_noon`、`cninfo_incremental_afternoon` | 3 |
| 02 | IRM 互动问答增量 | `irm_qa_incremental` | 1 |
| 03 | 成员关系入库 | `industry_membership_ingest`、`index_component_ingest` | 2 |
| 04 | PIT、基本面与业绩预告 | `pit_backfill`、`fundamentals_ingest`、`earnings_forecast_ingest` | 3 |
| 05 | 个股研究报告 | `research_stock_morning`、`research_stock_evening` | 2 |
| 06 | 行业研究报告 | `research_industry_morning`、`research_industry_evening` | 2 |

建议按 `01 → 02 → 03 → 04 → 05 → 06` 顺序执行。前四包先建立外部采集、手动入库和 PIT 类 Contract 的稳定模式；研究报告两包放在后面，避免在输入输出、完成标记和历史 Hermes 包装仍未澄清时过早抽象。

## 3. 明确排除

以下内容不属于本轮：

- 已封板的六条市场数据 Contract：`market_daily_update`、`adj_factor_daily`、`daily_basic_update`、`index_daily_update`、`zt_dt_pool_daily`、`suspend_d_ingest`；
- System B state、episode、pools。System B 是独立业务系统，不因源码位于 `pipeline/` 就纳入本轮 PipelineContract 批量重构；
- `pipeline_daily_summary_agent`、`system_health_weekly_agent` 及其计划中的确定性替代项；
- `qrp_production_daily_run`、System B pool completeness 等尚未实现的规划项；
- 历史修复、迁移、一次性 backfill 脚本，除已明确注册的通用 `pit_backfill` 能力；
- Hermes cron、systemd、部署选择清单、生产数据库、生产凭据和生产路径。

## 4. 全部工作包共同规则

每个工作包都必须：

1. 先读取当前工作区根目录可能存在的本地 `AGENTS.md`、`src/qrp_atlas/AGENTS.md`、`docs/QRP产品蓝图v1.1/12_Pipeline正式开发规则.md` 和 `deploy/pipeline/pipeline-registry.json`。
2. 从现有源码、测试、历史入口和可审计文档中提取真实业务语义；未知事实保持 `UNRESOLVED`，不得猜测。
3. 保留现有业务规则、表契约、PIT 语义和输出结果，不借合同化重构重新设计业务。
4. 正式实现使用 `PipelineContract` 和进程内 executor；不得为正式 Contract 新增 argv 子进程、结果 IPC 或第二套调度器。
5. 写 `quant.db` 的正式 Contract 统一使用 `quant_db_writer`；表级 DuckDB 资源只允许进入 `resource_reads`。
6. 将同一个 `ExecutionControl` 贯穿目标日期解析、检查器、外部 I/O 和写事务；外部请求、重试和等待不得超过剩余 deadline。
7. 明确参数、日期、输入、freshness、输出、completion、质量、幂等、事务、失败恢复、timeout、retry、性能预算和 `manual_execution_allowed`。
8. 仅在完整验收通过后加入默认 source catalog，并同步注册表中的迁移状态与证据。
9. 测试使用 `tmp_path`、临时 DuckDB、fixture 和 mock provider；不得访问生产数据库或真实外部服务。
10. 坚持反镀金原则：只修复妨碍本工作包正式合同化、真实运行或数据正确性的问题；通用化、未来多版本、额外审计平台和性能预优化不扩大范围。

## 5. 单包完成条件

每个工作包至少达到：

- 范围内每个 Pipeline ID 均有可发现、可描述、可执行的正式 Contract，或有基于当前事实的明确排除结论；
- 正常、空结果、结构缺失、provider 失败、部分返回、重复执行、事务失败、取消和 deadline 路径有专项测试；
- 真实输出行数、完成标记和 `PipelineResult` 一致；
- `qrp-atlas-jobs validate-contracts` 通过，现有六条市场数据 Contract 不回归；
- 相关 Pipeline 与 Orchestration 测试通过，`git diff --check` 通过；
- 不修改 Hermes、deploy 生产启用项或 System B；
- 提交完成报告，列出实际业务语义、修改文件、测试、未解决事实和非阻塞未来建议。

## 6. 提交与审查方式

每个工作包独立提交，继续留在 `feature/v1.1-pipeline-market-data-refactor`。完成一个工作包后先审查和返修，再进入下一包；不把六个工作包一次性堆成一个无法定位问题的大提交。
