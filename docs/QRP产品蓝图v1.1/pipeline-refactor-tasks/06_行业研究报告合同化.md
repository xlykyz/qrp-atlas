# 任务提示词｜行业研究报告合同化

## 工作目标

将以下两条行业研究报告能力正式接入 PipelineContract：

- `research_industry_morning`
- `research_industry_evening`

本任务在个股研究报告合同化之后执行，可以复用已经证明稳定的报告生命周期模式，但必须独立核对行业研究的输入、聚合、输出和完成语义，不能机械复制个股 Contract。

## 调查范围

重点调查：

- `src/qrp_atlas/pipeline/research_industry/`
- 行业分类、成员关系、行情及研究输出对应 contracts
- 相关 CLI、service、tests、报告文件和可审计历史 wrapper
- `deploy/pipeline/pipeline-registry.json` 中 morning/evening 两条记录
- 个股研究报告工作包已落地的通用报告边界
- Pipeline 正式开发规则

必须确认行业分类来源、成员快照时点、目标日期、晨间/晚间输入截止和聚合完成条件，确保不引入未来可见数据。

## 必须完成

1. 确认 morning 与 evening 的真实业务差异，默认保留两个稳定 ID；共享实现不得掩盖不同时间窗口和审计身份。
2. 为两个 ID 建立正式 `PipelineContract` 和进程内 executor，目标日期与时点由 `PipelineInvocation` / `TargetDatePolicy` 统一解析。
3. 精确声明行业成员关系、行情、研究或其他输入表及 freshness，确保成员关系和价格数据均符合 point-in-time。
4. 核对注册表中的 `external_hermes_agent`：只有实际参与确定性业务输入时才能保留；LLM 解释、总结或发送不得成为正式成功条件。
5. 明确行业聚合结果、数据库表、报告文件和可选投递之间的边界；所有正式 outputs 必须有 completion 和质量检查。
6. 明确同一目标时点重跑、行业成员变化、空行业、无有效成员、部分行业失败和历史保留语义。
7. 写 `quant.db` 时使用 `quant_db_writer`；成员、行情和其他只读表按实际对象进入 `resource_reads`。文件输出采用可恢复的提交方式。
8. 将同一个 `ExecutionControl` 贯穿输入读取、行业循环、聚合、文件生成和写事务；取消或到期后不得继续下一个行业或提交结果。
9. 输出标准 `PipelineResult`，至少记录行业数、成员数、读取/写入行数、文件 outputs、阶段耗时和质量检查。
10. 建立代表性全市场行业规模的本地性能基线，重点检查是否存在逐行业重复扫描全表的退化。
11. 完整验收后加入 source catalog，并更新注册表中的输入、完成标记、幂等、Agent 边界和性能证据。

## 测试要求

至少覆盖：

- morning/evening 注册、目标窗口和 PIT 成员语义；
- 行业成员表缺失、过期、空行业、无有效成员和成员跨期变化；
- 行情/研究输入缺失、字段错误和未来数据隔离；
- 正常数据库与报告文件输出；
- 同一目标重跑、部分行业失败和提交中断；
- 数据库与文件 outputs 的 completion 一致性；
- 可选通知或 LLM 不可用不影响正式结果；
- 取消/deadline 在读取前、行业循环中、文件提交前和写事务前生效；
- 全市场代表规模性能测试；
- 已注册全部正式 Contract 不回归。

测试不得访问生产数据库、真实外部服务、消息渠道或 LLM。

## 边界

- 不重新设计行业研究算法、行业分类体系、评分或展示模板。
- 不顺手修改 `industry_membership_ingest` 的业务规则；发现输入契约问题时只报告或做当前运行必需的最小兼容修复。
- 不建设通用报表平台、通知中心或 LLM 工作流。
- 不修改 Hermes、deploy 启用配置或 System B。
- 不为未来题材、概念或多分类体系提前扩展当前 Contract。

## 完成后汇报

汇报 morning/evening 差异、PIT 成员与输入 freshness、确定性输出、Agent/投递边界、完成和幂等、性能基线、测试结果、修改文件、注册表变化及未解决事实。不得部署或合并目标分支。
