# 任务 11：跨服务生产运行与最终验收

## 一、目标

把 v1.1 全部能力组织为可持续生产运行的系统，完成 qrp-atlas 与独立 qrp-trading 的调度、监控、告警、备份、恢复、连续 paper、MiniQMT 仿真、小资金实盘和发布候选验收。

本任务不新增交易规则、策略能力或网关通用功能，只验证已批准系统能够跨服务稳定、安全、可恢复地运行。

## 二、前置

- 任务 00—10-B 全部验收并合入 `develop/v1.1`；
- 正式生产规则和参数集已批准；
- 每日运行产品、`qrp-atlas/execution` 核心和 paper adapter 可用；
- 独立 qrp-trading 的生产窄协议、权限、幂等和事件契约已封板；
- qrp-atlas MiniQMT gateway adapter 已通过 READONLY 和仿真联调；
- qrp-trading 交付 commit、gateway version、protocol version 已锁定；
- 真实账户 LIVE mode 在 QRP 与网关两层仍默认关闭。

## 三、生产拓扑

```text
Linux / qrp-atlas
├── pipeline / contracts / indicators / strategies
├── production runtime
├── API / web
└── execution
    ├── business risk
    ├── OMS
    ├── recovery
    └── reconciliation
          │ versioned REST / WebSocket
          ▼
Windows / qrp-trading
├── auth / network gate
├── MiniQMT lifecycle
├── standard query/order/cancel protocol
├── event gateway
└── raw audit / logs
          │ xtquant
          ▼
MiniQMT / broker account
```

部署边界：

- qrp-atlas 是业务决策、订单计划和业务订单权威；
- qrp-trading 是 MiniQMT 边缘网关和原始券商事实入口；
- 两个服务不共享数据库；
- qrp-trading 不依赖 qrp-atlas 数据库；
- qrp-atlas 不直接读取 xtquant 或管理 Windows 网关生命周期；
- 券商账户是委托、成交、持仓和资金的最终现实事实；
- 所有跨服务调用均使用受控网络、认证和版本化协议。

## 四、生产调度

### 4.1 日历

- 使用正式交易日历；
- 处理周末、节假日、临时休市和特殊安排（数据可得时）；
- 所有任务明确业务日期和时区；
- 不使用简单自然日加减替代交易日映射；
- QRP 与网关时钟偏差纳入健康检查；
- 网关服务器时间、QRP时间和券商事件时间分别记录。

### 4.2 固定运行时序

具体时点进入环境配置，但职责顺序固定：

```text
盘前
→ QRP/网关健康与协议兼容检查
→ QMT连接、账户订阅和事件新鲜度检查
→ 前日对账、活动订单、UNKNOWN和外部人工交易检查
→ 账户/持仓/资金快照
→ 冻结计划有效性与业务风险门

执行窗口
→ QRP execution提交标准命令
→ qrp-trading转发MiniQMT
→ REST确认 + WebSocket事件 + 主动查询
→ OMS状态迁移和异常门禁

盘中
→ 活动订单、成交、连接和事件流监控
→ 制度化撤单、暂停和kill switch
→ 不重新选股、不重算目标、不盘中主观加单

收盘后
→ 行情与研究数据更新
→ 水位、状态、授权、题材、角色、策略、目标和次日计划
→ 冻结规则、参数和输入快照

日结
→ 查询最终资产、持仓、委托和成交
→ QRP/网关/券商三方对账
→ 关闭当日execution run
→ 复盘、归因、备份和报告
```

### 4.3 依赖 DAG

```text
source data
→ contracts validation
→ data watermarks
→ indicators
→ authorization / themes / roles
→ strategy decisions / portfolio target
→ frozen order plan
→ qrp-atlas execution recovery gate
→ qrp-trading health / capability gate
→ standard order commands
→ broker orders / fills
→ three-party reconciliation
→ closeout
```

上游未成功，下游不得无条件运行。

### 4.4 触发和幂等

支持：

- 手动受控触发；
- 定时触发；
- 业务日期幂等；
- 阶段级重试；
- 从安全检查点恢复；
- 取消；
- 超时；
- 单实例/分布式锁；
- 运行历史；
- owner/account隔离。

特别约束：

- 普通任务重试不得等同重新下单；
- submit/cancel重试必须复用原`request_id`；
- 未知结果先查询网关/券商，不创建新订单；
- 网关重启后幂等记录和原始审计必须可恢复；
- 新attempt只能由QRP创建新generation并审计。

## 七、告警

分级：

```text

WARNING
ERROR

```

CRITICAL至少包括：

- LIVE期间QMT断线且有活动订单；
- qrp-trading不可达且存在SUBMITTING/UNKNOWN；
- WebSocket断线且主动查询也失败；
- UNKNOWN订单无法通过查询恢复；
- QRP/网关/券商订单映射丢失；
- 三方重大对账差异；
- 重复订单风险；
- 账户别名或模式不匹配；
- 数据水位不足但计划被尝试执行；

- capability hash非预期变化；
- QRP或网关kill switch失败；
- 订单/成交/审计持久化失败；
- 备份和恢复关键失败；
- API Key泄露迹象或异常来源IP。

告警必须：

- 去重和聚合；
- 带production run、execution run、client order、gateway request和account alias引用；
- 不包含明文凭证和完整账户号；
- 有确认、处置和关闭状态；

## 十、安全与远程访问

- qrp-trading仅绑定受控局域网接口；
- Windows防火墙限制指定网段或Linux主机；
- 外出访问通过加密虚拟局域网或认证隧道；
- 不直接暴露qrp-trading、MiniQMT或QRP写接口到公网；
- READONLY/TRADE/ADMIN最小权限；
- QRP服务使用专用API Key，不复用人工ADMIN Key；
- 密钥可轮换、可撤销；
- 研究用户和execution写权限分离；
- secrets使用环境或安全存储；
- 依赖、配置、日志和审计安全检查；
- 前端不得获取网关API Key或直接调用网关；
- 通用RPC不进入生产OMS路径。

## 十四、release分支与冻结

全部工作包合入`develop/v1.1`后：

```text
develop/v1.1
→ create release/v1.1-acceptance
→ lock qrp-atlas head
→ lock qrp-trading commit/version/protocol
→ execute final acceptance
→ only acceptance fixes allowed
→ PR release/v1.1-acceptance → main
→ tag v1.1.0 after approval
```

验收期间禁止：

- 新增功能；
- 修改交易规则以改善近期结果；
- 改变跨仓边界；
- 扩大账户或资金；
- 升级协议而不重新验收；
- 自动合并、打tag或创建Release。
