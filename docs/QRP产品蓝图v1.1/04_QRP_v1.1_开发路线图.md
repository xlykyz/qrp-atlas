# QRP v1.1 开发路线图

> 状态：范围基线草案。  
> 原则：任务按依赖顺序执行，不并行推进主线，不以中间可用状态替代完整产品终点。  
> 长期集成分支：`develop/v1.1`。

## 一、路线原则

1. 先冻结规则、范围和验收，再改运行代码；
2. 一次只推进一个正式任务或一个已批准子任务；
3. 上游契约未完成，下游不得以临时字段或口头约定开工；
4. 事实、资格、评分、决策、执行和评价严格分离；
5. 先完成历史可复算，再接每日生产；
6. 先完成 qrp-atlas 券商无关 execution 核心，再封板 qrp-trading 生产协议；
7. 先 paper、只读联调和仿真，再小资金实盘；
8. 每个任务必须形成端到端测试、失败路径和验收报告；
9. 新想法通过变更控制，不直接插入当前任务；
10. 任务完成后同步能力矩阵、路线图和总体验收清单；
11. v1.1工作包不直接向main提PR；
12. 两个仓库的跨服务交付分别提交、统一验收。

## 三、阶段划分

### 阶段0：范围与规则基线

包含任务00。

退出条件：

- 规则资产完整；
- 冲突全部裁决或明确标记为不进入v1.1；
- System A/B/C定位冻结；
- 判断层、资格、评分、仓位和退出边界冻结；
- execution与qrp-trading跨仓边界冻结；
- 所有工作包输入、输出和验收冻结；
- 变更控制正式生效。

### 阶段1：标准事实与状态

包含任务01—03。

目标：

```text
规则与生产契约
→ 历史全A与可交易性
→ 全市场System B和市场状态事实
```

退出条件：

- 任意历史交易日可生成当时全A股票池；
- 可交易性事实可PIT查询；
- System B生命周期对全市场逐日可复算；
- 不依赖账户持仓；
- 数据缺失和停牌语义明确；
- 兼容现有基础字段和策略。

### 阶段2：授权、题材与角色

包含任务04—06。

目标：

```text
市场判断与授权
+ 动态产业—题材周期
+ M1/M2/M3核心身份
```

退出条件：

- 判断层只授权新开仓且可历史回放；
- 题材库完成正式PIT代码链；
- 角色绑定`theme_cycle`；
- 角色分数、置信度和证据可查询；
- 人工/Agent变更走proposal和审核，不直写canonical。

### 阶段3：完整策略与验证

包含任务07—08。

目标：

```text
授权 ∩ 题材 ∩ 角色 ∩ 趋势 ∩ 可交易性 ∩ 风险
→ eligible
→ score / rank
→ full portfolio target
→ complete-system validation
```

退出条件：

- eligibility与rank分离；
- 空池子合法；
- 所有淘汰原因可解释；
- 目标组合确定性；
- 完整周期、walk-forward、成本、容量和规则归因通过；
- 生产配置可replay。

### 阶段4：每日产品

包含任务09。

退出条件：

- 每日生产运行可从数据水位到订单计划完整执行；
- 运行包可重新打开；
- 前端解释市场授权、题材、角色、资格、评分和目标；
- 计划可冻结和取消；
- 尚不发送真实订单。

### 阶段5：执行编排与网关联调

包含任务10-A、10-B。

任务10-A退出条件：

- `execution`不依赖具体券商或Windows环境；
- 目标到订单、业务风险、幂等、状态机、恢复和对账完整；
- paper模式通过；
- 不import xtquant；
- 不直接连接MiniQMT。

任务10-B退出条件：

- qrp-trading生产窄协议、版本、错误码和幂等封板；
- qrp-atlas MiniQMT gateway adapter实现标准协议；
- READONLY局域网联调通过；
- 网关交易关闭时正确拒绝；
- 仿真查询、下单、撤单、事件和重连通过；
- 断线、部分成交、拒单和重启不产生重复订单；
- QRP、网关、券商三方对账成立。

### 阶段6：生产验收

包含任务11。

退出条件：

- 跨服务调度、监控、备份和恢复通过；
- 连续paper和仿真运行通过；
- 受限小资金实盘通过；
- 日结对账无未解释差异；
- 全量测试、构建、协议兼容和安全审计通过；
- 最终验收PR获人工授权。

## 五、分支治理

### 5.1 qrp-atlas

```text
main
└── develop/v1.1
    ├── feat/v1.1-wp00-...
    ├── feat/v1.1-wp01-...
    ├── ...
    └── release/v1.1-acceptance
            └── PR → main → tag v1.1.0
```

规则：

- 每个工作包从最新`develop/v1.1`创建；
- 每个工作包PR目标为`develop/v1.1`；
- 工作包不得直接向`main`提PR；
- `main`仅接受v1.0严重缺陷、安全和生产阻塞修复；
- main修复通过普通merge同步到`develop/v1.1`；
- 禁止对长期集成分支rebase或force push；
- 全部工作包完成后创建`release/v1.1-acceptance`；
- 验收分支只允许验收修复，最终版本级PR合入main。

### 5.2 qrp-trading

qrp-trading保持独立本地仓库：

- 任务10-B在该仓库使用独立功能分支和提交；
- 网关版本、commit、协议版本和测试结果写入跨仓验收报告；
- 不把网关代码复制进qrp-atlas；
- 若未来上传GitHub，默认仍保持独立仓库和独立发布版本；
- 跨仓工作包可统一验收，但不能伪装成单仓原子提交。

## 六、任务并行规则

主线默认串行。只有满足以下条件才允许并行：

- 两个任务不修改同一公共契约；
- 不存在输入输出依赖；
- 已指定独立负责人、分支和验收；
- 不会造成同一业务规则两套实现；
- 并行获得人工明确授权。

任务10-B内部允许两个仓库按已封板协议分别实现，但协议契约必须先冻结，最终统一联调；这不改变v1.1主线串行原则。

未经授权，不因多台开发机或多个Agent自动并行。

## 七、每个任务统一退出条件

每项任务至少满足：

- 需求和边界与蓝图一致；
- 公共契约更新完整；
- 正式实现和公开导出完整；
- 单元、集成、PIT、失败路径和回归测试完整；
- 无未来函数；
- owner隔离适用时通过；
- 稳定reason code/diagnostic code；
- 文档、能力矩阵和验收清单更新；
- 专项测试、全量pytest、compileall、diff check通过；
- 涉及前端时lint、typecheck、test、build通过；
- 涉及网关时协议兼容、鉴权、幂等和断线恢复通过；
- 工作树干净；
- PR未自行合并，等待独立验收。

## 八、禁止跨越的门禁

- 任务00未完成，不得实现正式规则；
- 任务01未完成，不得新增临时生产表；
- 任务02未完成，不得宣称全市场回测；
- 任务05未完成，不得把临时供应商概念标签当canonical题材；
- 任务07未完成，不得生成正式实盘订单计划；
- 任务08未完成，不得用单次回测结果授权实盘；
- 任务09未完成，不得让execution或qrp-trading自行拼装策略输入；
- 任务10-A未完成，不得把冻结计划直接发送到qrp-trading；
- 任务10-B生产协议未封板，不得用通用RPC充当正式OMS下单路径；
- 任务10-B仿真未通过，不得接正式账户；
- 任务11未验收，不得宣告v1.1完成。
