# 任务 05：动态产业—题材库代码化

## 一、目标

将 `docs/动态产业题材库v0.1/` 中已验收的实体、PIT、事实/评分分离、生命周期、proposal 和 owner 设计完整落为正式代码、数据库、查询、指标、API 和基础产品链。

本任务不是建立一个供应商概念标签表，也不是仅做题材名称与股票列表。

## 二、前置

- 任务 01、02 已验收；
- 动态题材库现有设计作为业务契约输入；
- 任务 00 已明确题材授权与 System B 的关系；
- 数据来源和许可边界已确认。

## 三、必须实现的分层

```text
L0 Source Snapshot
L1 Canonical Fact
L2 Curated Knowledge
L3 Derived Signal
L4 Serving View
Owner-Private Workspace
```

要求：

- L0/L1 只通过 pipeline/contracts 写入；
- L2 的人工/Agent 操作先生成 proposal；
- L3 可由固定输入重算；
- L4 只做服务视图，不成为 PIT 权威；
- owner 私有对象不污染全局 canonical。

## 四、实体和关系

正式实现：

```text
taxonomy_node / chain_node
chain_edge
asset_chain_relation
theme
theme_version
theme_alias
theme_cycle
theme_chain_link
theme_membership
source_document / source_excerpt
catalyst_event / event_theme_link
evidence_link
```

关键边界：

```text
ASSET ↔ CHAIN_NODE     长期业务事实
THEME ↔ CHAIN_NODE     某轮题材影响产业环节
THEME ↔ ASSET          市场成员事实
THEME ↔ THEME_CYCLE    每轮独立周期
```

不得把公司—产业关系绑死在某个题材成员上。

## 五、事实与观察分离

`theme_membership` 只保存成员关系事实和证据，不保存会随市场变化的最终分数、排名和角色。

动态观察分别进入：

```text
member_metric_observation
member_role_observation
theme_metric_observation
theme_lifecycle_transition
```

要求：

- 同一成员事实可跨多个日期观察；
- 分数和角色带 calculation version、coverage 和 as_of；
- 事实修订不覆盖历史版本；
- 反证和否认可表达；
- 未知不等于否定。

## 六、PIT 与双时态

每类事实按适用范围保留：

```text
published_at
available_at
available_trade_date
observed_at
ingested_at
effective_from / effective_to
valid_from / valid_to
revision_id
```

查询至少支持：

- `strict_effective`：严格按市场可用与业务有效时间；
- `observed_as_of`：按 QRP 当时已观察/认可信息；
- 审计全部修订；
- 禁止未来成员、未来别名、未来证据和未来生命周期泄漏。

## 七、题材周期和生命周期

实体治理状态：

```text
active / archived / merged / invalid
```

市场生命周期：

```text
candidate
emerging
active
accelerating
diverging
cooling
dormant
```

要求：

- 实体治理与市场生命周期分离；
- “复燃”创建新 `theme_cycle`，不加入 `reactivated` 状态；
- 迁移绑定 cycle_id；
- 至少两个独立信号维度触发重要迁移；
- 滞回、最短停留期和 coverage 明确；
- 模型先生成 proposed transition，提交器校验后写正式迁移。

## 八、题材指标

实现并版本化：

```text
catalyst_score
attention_score
strength_score
breadth_score
leadership_score
capital_score
evidence_score
novelty_score
crowding_score
risk_score
theme_activity_score
```

必须：

- components、coverage、calculation version 完整；
- 缺失不按 0；
- 风险与活跃并列；
- 供应商黑盒分数权重受控；
- 题材规模偏差处理；
- 日频与盘中基线不混用；
- v1.1 正式主线先完成盘后日频闭环，盘中仅在蓝图明确范围内增强。

## 九、成员双轴

业务相关度与市场共振度分开：

```text
business_relevance
market_resonance
```

业务相关度来自：证据质量、营收/产能暴露、产业角色、时效、来源独立性和反证。

市场共振度来自：残差收益、量能扩张、共振、领涨持续性和注意力。

未知暴露降低 coverage，不自动赋 0。

## 十、proposal 与 Agent

正式实现：

```text
proposal
proposal_item
review_task
review_decision
canonical_commit
audit_log
agent_run
```

Agent 规则：

- 默认只读；
- 每个主张带来源和定位；
- 可建议新题材、别名、成员、产业关系、证据和合并；
- 不得直接改 canonical；
- 不得仅凭价格共振证明产业关系；
- 失败或低置信提案进入审核队列；
- owner 私有 agent run 隔离。

## 十一、运行链

盘后日频至少形成：

```text
来源采集
→ 快照与内容哈希
→ 标准实体/事件/关系
→ 日快照差分
→ 指标
→ 生命周期候选迁移
→ 变化事件
→ 审核/提交
→ API / serving view
```

每层保存运行状态。上游失败不得被下游解释为无变化。

## 十二、API 与基础前端

API 至少支持：

- 题材列表和 as_of 查询；
- 题材详情、版本和周期；
- 成员、产业链、证据和反证；
- 指标和生命周期；
- 历史时间线；
- 变化事件；
- proposal/review；
- owner 私有笔记和订阅（按范围）；
- 数据 coverage 和血缘。

前端以既有动态题材库原型为视觉与交互基线，正式产品整合在任务 09 完成。

## 十三、测试

覆盖：

- 实体去重、别名冲突和合并；
- 产业/题材/成员关系隔离；
- PIT、修订和双时态；
- cycle 复燃；
- 生命周期合法/非法迁移；
- coverage 与缺失；
- 分数可重算；
- proposal 审核和不可直写；
- owner 隔离；
- 来源许可/保留策略；
- 上游失败；
- API 和历史回放；
- Agent 每项主张引用。

## 十四、禁止范围

- 不把题材 activity 直接当收益预测；
- 不在本任务生成 System B 交易动作；
- 不用单一供应商替代 canonical；
- 不用向量相似度自动提交合并；
- 不建立图数据库依赖作为首期前置；
- 不允许 Agent 无审核写事实；
- 不将 price cluster 当产业关系证据。

## 十五、验收

- 现有题材库文档中的五项核心契约全部代码化；
- 任意历史日期可查询当时题材、成员、证据、指标和生命周期；
- 事实、评分、角色和治理状态不混淆；
- proposal/owner/PIT 完整；
- 盘后日频闭环可运行；
- 专项、全量、API 和回放测试通过；
- PR 等待独立验收。
