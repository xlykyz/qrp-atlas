## 1. 目标与非目标

### 1.1 目标

Task09 必须完成以下**开发工作**：

1. 从 formal System B strategy 的真实输入要求反推并冻结代码侧 Contract Graph；
2. 明确哪些既有 `PipelineContract` 是 strategy daily 的正式上游，并在代码中声明唯一依赖语义；
3. 建立正式 `system_b_strategy_daily` Contract，作为 strategy 层进入 Pipeline Runtime 的最薄 adapter；
4. 复用 Task05 / Task06 / Task07 已有 authorization、decision、portfolio semantics，生成每日完整 `StrategyPortfolioTarget`；
5. 为 strategy result / final target 建立稳定、可审计、可确定性重放的持久化或正式引用语义；
6. 建立薄的 `system_b_daily_closeout` Contract，作为“某交易日 System B 正式产品结果已完整形成”的代码侧完成标记；
7. 保证 target date、rule / parameter / strategy version、upstream provenance、target identity 可追溯；
8. 通过单元、集成、离线端到端和 deterministic replay 测试证明代码闭环成立。

### 1.2 非目标

Task09 明确不做：

- 修改生产 `production-job-definitions.json`；
- 新增或启用任何真实 Production Job instance；
- 决定或修改 schedule / cron；
- 修改、安装或部署 `qrp-atlas-jobs.service`；
- SSH 到生产机执行发布；
- enable / disable / start / stop / restart 任意服务；
- 迁移 production authority；
- 连续生产 daily run；
- 生产补跑、回滚和发布观察；
- 新 Scheduler；
- 新 Job Runner；
- 新 DAG / workflow engine；
- 新的 `SYSTEM_B_DAILY = [stage...]` 第二套声明体系；
- 在一个 Python 函数里硬编码整条 daily 调用顺序；
- 把 authorization / score / decision / portfolio resolver 分别包装成独立 Pipeline Job；
- execution / broker / OMS / order plan / 实盘权限；
- 顺带修复所有历史生产 defect 或 legacy 运维残留。

> **硬 Scope Rule**：凡是需要修改生产环境、调度实例、运行时服务或实际 schedule 才能完成的事项，都不属于 Task09 开发任务。

### 5.1 Audit 目标

对每个候选上游回答：

### 5.3 Audit 输出

Phase 1 冻结的依赖边界如下。`market_phase` 是直接读取的正式表事实，不增加一个只为转发它的 Pipeline；题材 rank、M4/M5/M6 不是当前 `SystemBPortfolioStrategy` 的直接输入，不加入本 Contract 的依赖。

```text
system_b_strategy_daily.dependencies = (
    system_b_state_daily,
    system_b_episode_rebuild,
    system_b_pool_height,
    system_b_pool_capacity,
    system_b_pool_recognition,
    system_b_asset_rank_daily,
    system_b_decision_facts_daily,
)
```

`system_b_decision_facts_daily` 是本次冻结的最小前置事实 interface Contract，负责以统一 envelope 暴露候选资格、比较分、退出触发和严重异动监督状态。Task09 必须实现并注册这个边界的 schema、版本、provenance、availability 和 target-date 语义；不要求在 Task09 内完成每个字段背后的最终业务 producer。字段可以是当前 v0.1、明确 `UNAVAILABLE`，或标记为后续业务能力。这个选择基于事实具有独立的每日快照、版本和 freshness 生命周期，而不是因为 adapter 方便而机械拆分。

依赖理由：

| Dependency | 业务输入理由 | 当前状态 |
|---|---|---|
| `system_b_state_daily` | 状态观察、MA5/实际交易日序列、状态 provenance；为退出触发事实提供上游依据 | 已注册 |
| `system_b_episode_rebuild` | episode 生命周期事实，供池与决策事实的候选域审计 | 已注册 |
| `system_b_pool_height` | HEIGHT 池完成标记与成员快照 | 已注册 |
| `system_b_pool_capacity` | CAPACITY 池完成标记与成员快照 | 已注册 |
| `system_b_pool_recognition` | RECOGNITION 池完成标记与成员快照 | 已注册 |
| `system_b_asset_rank_daily` | M1/M2/M3 资产 rank 快照及其输入 provenance；不得改名充当 comparison score | 已注册 |
| `system_b_decision_facts_daily` | 将 score/eligibility/exit/supervision/candidate facts 以同一 trade date、snapshot、版本和 availability 交付 | **Task09 interface 必须实现/注册；具体 producer 可后续演进** |

直接表输入 `quant_db.market_phase` 提供 `phase` 与 `V_triggered`，不形成 dependency；`holdings` 由调用方提供的不可变 prior-state snapshot 交付，也不形成 dependency。

**Task09 只要求 dependency 指向已注册、语义正确的 pipeline_id。**

因此当前 registry 缺少的是正式 decision-facts interface registration，而不是所有业务事实 producer 的成熟实现。Phase 2 可以先闭合 interface、adapter、strategy、target 和 closeout；生产 Daily readiness 另行检查必要字段是否 `AVAILABLE`。

### 5.5 Authorization Source（冻结）

授权链固定为：

```text
quant_db.market_phase.phase + quant_db.market_phase.V_triggered
        ↓
SystemBAuthorizationStrategy
        ↓
authorization status
        ↓
SystemBPortfolioStrategy
```

`phase` 与 `V_triggered` 的语义 owner 都是 market phase producer；Task09 不新增 authorization PipelineContract 或独立授权表。authorization 在同一次 strategy invocation 内计算，并作为完整、带版本的 authorization result 持久化在 strategy result 的 `authorization_json` 中，不单独成为业务结果 SSOT。

runtime context precedence 保持 Task07-C：`runtime_context` 中的 authorization、candidate set 和 comparison-score provenance 优先于 parameters；两者均缺失时为 `UNAVAILABLE`，不得默认 authorized。portfolio 只能消费 typed authorization status；缺失、过期或冲突均 fail-closed。目标日期由 invocation envelope 统一提供，不能从 authorization 输入另行推导。

Task09 adapter 必须显式传入已校验的 candidate set；不得触发现有 portfolio 在 candidate 缺失时“所有非持仓 ticker”回退路径。candidate snapshot 缺失或与 prepared facts domain 不一致时，在 strategy invocation 前拒绝执行。

### 5.6 Result / Target / Closeout Persistence（冻结）

现有 `StrategyPortfolioTarget`、`StrategyRunResult` 只能表达内存结果，不能表达稳定 identity、digest、provenance 或 closeout；现有 `job_run` 也只是运行基础设施，禁止作为业务结果 SSOT。因此冻结并实现以下最小业务模型。

`system_b_strategy_result`：

| Column | Contract |
|---|---|
| `strategy_run_id` | PK；`sha256(canonical invocation envelope)`，不含 `created_at` |
| `trade_date` | `DATE NOT NULL`，遵循 5.8 日期合同 |
| `strategy_code`, `strategy_version` | `NOT NULL` |
| `rule_version_set_id`, `parameter_set_id`, `input_snapshot_id` | `NOT NULL`，完整 provenance identity |
| `parameters_json`, `authorization_json`, `result_json` | canonical JSON；result 必须能重建 complete target 引用 |
| `result_digest` | result envelope 的 SHA-256 lowercase hex |
| `result_status` | `SUCCESS` / `NO_OP` / `FAILED` |
| `created_at` | 审计时间，不参与任何 identity |

`strategy_run_id` 的 invocation envelope 固定包含 schema=`system_b_strategy_invocation@1`、trade_date、strategy code/version、rule/parameter/input snapshot identity、完整 comparison-score provenance、canonical parameters、authorization input/status、candidate set 和 canonical prior holdings；使用与 5.7 相同的 UTF-8 compact sorted-key JSON 与 SHA-256，排除 created_at、Job Runtime `run_id` 与 `invocation_id`。同一业务 envelope 即使由不同 runtime run 执行也必须得到同一 identity。`result_digest` 对 schema=`system_b_strategy_result@1`、strategy_run_id、result_status、authorization_json、canonical decisions 和 target_digest 做同样 canonical serialization；diagnostics 只能作为审计字段，不能改变业务 target identity。

业务唯一键为 `(trade_date, strategy_code, strategy_version, rule_version_set_id, parameter_set_id, input_snapshot_id)`。同一 invocation envelope 的 rerun 必须得到同一 `strategy_run_id`；输入、规则、参数或 strategy version 任一变化都创建新 immutable row。历史成功或失败结果均不可 update/overwrite。

`system_b_strategy_target`：

```text
PRIMARY KEY (strategy_run_id, target_identity)
trade_date DATE NOT NULL
strategy_code TEXT NOT NULL
strategy_version TEXT NOT NULL
target_kind TEXT NOT NULL              # PORTFOLIO / NO_OP
target_identity TEXT NOT NULL       # 等于 target_digest
target_digest TEXT NOT NULL         # 5.7 canonical target SHA-256
canonical_target_json TEXT NOT NULL
created_at TIMESTAMP NOT NULL
```

一个 strategy run 只能有一个 target；`strategy_target.strategy_run_id` 外键引用 strategy result，且 target 的 trade_date/code/version 必须逐项相等。同一 digest 可被不同 provenance 的 run 引用，但不得覆盖旧行。`FAILED` run 不得伪造 target；交易日无持仓时以 `target_kind=PORTFOLIO`、positions=`[]` 的完整空 target 表达。非交易日使用 `target_kind=NO_OP` 的不可执行空 target 仅供 closeout 引用，result/closeout 为 `NO_OP`，绝不解释为清仓指令。

`system_b_daily_closeout`：

```text
closeout_identity TEXT PRIMARY KEY  # sha256(canonical closeout envelope including status/result digest)
trade_date DATE NOT NULL
strategy_code TEXT NOT NULL
strategy_version TEXT NOT NULL
strategy_run_id TEXT NOT NULL
target_identity TEXT NOT NULL
target_digest TEXT NOT NULL
rule_version_set_id TEXT NOT NULL
parameter_set_id TEXT NOT NULL
input_snapshot_id TEXT NOT NULL
completion_identity TEXT NOT NULL
completion_status TEXT NOT NULL      # SUCCESS / NO_OP / FAILED
completed_at TIMESTAMP NOT NULL
created_at TIMESTAMP NOT NULL
```

closeout 的业务唯一键为 `(trade_date, strategy_run_id, target_identity, completion_status)`；`strategy_run_id` 与 `target_identity` 外键引用对应 result/target，且 date/code/version/digest 必须匹配。相同版本重复 closeout 是幂等 no-op，identity 冲突或 target 不匹配必须失败且不修改既有行。strategy result 与 target 在同一事务中原子写入；closeout 在读取并校验二者后单独事务写入。任一异常都 rollback 当前事务，不回滚或改写历史 immutable 结果。`job_run`/`job_result` 仅用于调度运行观测，不承担上述业务事实。

### 5.7 Canonical Target Digest（冻结）

唯一 canonical payload 为 UTF-8 JSON（下例展示 sort_keys=true 后的键序）：

```json
{"positions":[{"asset_id":"...","reason_code":"...","target_weight":"0.125000000000"}],"schema":"system_b_target@1","strategy_code":"system_b_portfolio","strategy_version":"1.0.0","trade_date":"YYYY-MM-DD"}
```

规则固定如下：

- positions 按 `asset_id` 的 Unicode code-point 升序排列；asset_id 非空且不可重复。
- weight 必须 finite；先用 `Decimal(str(value))`，按 `0.000000000001` 以 `ROUND_HALF_EVEN` 量化，再输出固定 12 位小数字符串。
- 必须包含 schema、trade_date、strategy_code、strategy_version、asset_id、reason_code、target_weight；不包含 diagnostics、evidence、input provenance、run identity、created_at。
- 使用 `ensure_ascii=false`、`sort_keys=true`、`separators=(',', ':')`，不追加换行；hash 为 SHA-256 lowercase hex。
- 空 target 统一表示为 `positions: []`，不是 null 或缺字段。

固定 golden fixtures：

| Fixture | Canonical input | Expected digest |
|---|---|---|
| T0 | 2024-01-10, system_b_portfolio@1.0.0, empty positions | `9bb5e39176a402d3eb1e90b4cc6fff20a4ecd637cd6e83c8b1ffd9d9e8f93a28` |
| T1 | H1=`0.250000000000` ADD_ENTRY_SELECTED; N1=`0.125000000000` NEW_ENTRY_SELECTED | `207bca336ac555e2a00f1a40e5249f09e476ff6b197714dfdfa788a640ef055b` |
| T2 | A=`0.1250000000004` quantizes to `0.125000000000`; B=`0.1250000000006` quantizes to `0.125000000001`; both reason `HOLD` | `6b8b2281011ac4095ac50a7727b72f79cc4e76c83e3d742aa661ac33e66f0a82` |

因此 Python dict insertion order、不同 JSON key order 或等价 float 表达不得改变 digest。

### 5.8 Target Date Policy（冻结）

- scheduled invocation 必须接收 timezone-aware `scheduled_for`，转换为 `Asia/Shanghai` local date；naive datetime fail-closed。
- `explicit trade_date override` 优先于 scheduled date，且只接受严格 date-only 值：`isinstance(value, date) and not isinstance(value, datetime)`；datetime、字符串和其他类型一律拒绝，不隐式 parse。
- historical/manual invocation 也必须显式提供该 date，禁止读取运行时“今天”或从 upstream timestamp 推导。
- 采用 `ALLOW_CALENDAR_DATE`：非交易日保留请求日期，不回退前一交易日；strategy result 与 closeout 均为 `NO_OP`，不得生成清仓空 target。交易日无持仓可以生成 canonical empty target。
- 统一 helper 只在 Task09/调用边界做严格 date-only 兼容修正；不扩展为全仓日期框架重构。现有 `system_b_contracts._validate_target_date` 对 datetime 过宽，Task09 不得沿用该宽松语义。

### 5.9 Task08 ↔ Task09 Parity Fixture（冻结）

后续自动化测试直接使用以下 fixture；Task08 formal replay 与 Task09 daily adapter 必须在同一输入/version 下得到相同 canonical target JSON 与 digest，比较 canonical representation，不比较 Python object identity。

## 6. 冻结设计决策

### D01 — 不新增第二套 orchestration

`PipelineContract` 是业务依赖唯一代码 SSOT。

Task09 不实现新的 DAG、workflow definition 或 System B 私有 Runner。

### D02 — Task09 结束于可挂载 Contract

Task09 的交付边界是：

```text
registered formal Contract
+ tested executor
+ stable inputs / outputs
+ deterministic semantics
+ documented dependencies
```

不包含 production instance / schedule / service deployment。

### D03 — Strategy 内部语义保持封装

以下继续作为 formal strategy 内部组件，不拆独立 Pipeline Contract：

```text
authorization
score / comparison
entry / exit decision
portfolio constraint resolution
```

除非实现过程中出现新的、可证明的独立持久化生命周期，否则不得为了“流程看起来清楚”而拆分。

### D04 — 新增 `system_b_strategy_daily`

Task09 引入：

```text
pipeline_id = system_b_strategy_daily
```

职责严格限定为 production-compatible adapter：

1. 解析 target trade date；
2. 读取 formal upstream facts；
3. 校验 freshness / version / required input；
4. 构建正式 `StrategyInput`；
5. 调用现有 formal System B strategy；
6. 得到完整 `StrategyPortfolioTarget`；
7. 保存或正式引用 strategy result / target；
8. 输出结构化 provenance 与 diagnostics。

禁止：

- 复制 Task05 / 06 / 07 业务规则；
- Task09 私自默认 authorization；
- 对缺失 rank / facts 静默降级；
- 把完整 target 降级成零散 buy/sell signals。

### D05 — 新增 `system_b_daily_closeout`

Task09 引入：

```text
pipeline_id = system_b_daily_closeout
```

它是一个**代码侧 terminal Contract**，不是调度器。

职责：

- 验证 `system_b_strategy_daily` 的正式结果存在且完成；
- 验证目标日期一致；
- 验证 rule / parameter / strategy version provenance 可解析；
- 验证 final target identity / digest 可解析；
- 写入或生成唯一 daily completion result。

Closeout 不重新计算 market / theme / rank / strategy / target。

### D06 — Fail-Closed 保持到底

以下情况不得生成“尽量可用”的正式 target：

```text
required input missing
required upstream output missing
freshness failed
version incompatible
authorization unavailable
strategy validation failed
target cannot be resolved
```

必须返回明确结构化失败。

这里的 `required input missing` 指正式 interface envelope、schema/version、trade_date、provenance 或 availability 状态本身缺失/非法；它不等同于字段状态被正式标记为 `UNAVAILABLE`。后者必须沿用各 strategy fact 的明确 fail-closed 业务语义（例如 no NEW/ADD、保留既有 exposure 或不可执行 NO_OP），不得伪造可用值。

### D07 — Determinism 优先于便利

同一：

```text
trade_date
input snapshot
rule version set
parameter set
strategy version
```

必须得到一致且可解释的 strategy result / target identity。

Task08 historical replay 与 Task09 daily adapter 必须共享同一 strategy / target 业务语义。

### D08 — Production defect 不进入本开发任务

调研中发现的 ETF、stock-basic、Hermes legacy、manifest drift、systemd unit 等生产问题，不因 Task09 存在而自动升级为开发 blocker。

只有当某个缺陷被证明是 **Task09 新 Contract 的代码输入契约本身错误** 时，才以最小 defect patch 进入本任务。

## 7. `system_b_strategy_daily` 详细契约要求

### 7.1 Target Date

必须使用正式 `TargetDatePolicy`。

要求：

- explicit trade date 与 scheduled date 的解析规则唯一；
- 时区明确为 `Asia/Shanghai`；
- 非交易日行为明确，不允许隐式把“今天”替换成上一个交易日；
- historical/manual invocation 与 scheduled invocation 使用同一解释源。

### 7.2 Inputs

输入必须全部通过 formal `InputContract` / freshness 表达。

至少区分：

```text
market / state facts
pool / episode facts
asset / theme rank facts
market authorization facts
strategy state / prior holding state
rule / parameter / strategy version provenance
```

最终 inputs 已由 5.4 Formal Strategy Input Matrix 冻结；实现只能按该表消费正式事实，不得在 adapter 内补写 score、eligibility、exit 或 supervision 规则。

### 7.3 Authorization

沿用 Task07-C 语义：

```text
missing  -> UNAVAILABLE -> no NEW / ADD
explicit false -> DENIED
runtime context > parameters
```

Task09 adapter 不得注入 `AUTHORIZED` 默认值。

### 7.4 Strategy execution

必须通过现有 strategy registry / validation 路径执行正式 System B strategy。

不得直接 import 一组内部函数后自行拼装另一套业务路径。

### 7.5 Target

正式输出必须是**完整目标组合**，而不是动作碎片。

需要能回答：

```text
某日最终持有哪些资产？
每个资产 target weight 是多少？
哪些是 HOLD / NEW / ADD / EXIT 的业务来源？
用了哪份 strategy / rule / parameter version？
```

### 7.6 Persistence / Provenance

优先复用现有正式结果 / target 持久化能力。

若现有 schema 不能表达 Task09 所需 provenance，允许新增**最小必要** Contract / table，但必须遵守：

- 不覆盖历史结果；
- 同 trade date 重跑有明确 replacement / version 语义；
- target identity 可稳定计算；
- strategy run 与 target 可关联；
- 输入 / 版本 provenance 可审计；
- 不把 Job Runtime 自身的运行状态表当业务结果 SSOT。

## 8. `system_b_daily_closeout` 详细契约要求

### 8.1 目的

回答唯一问题：

> 某个 trade date 的 System B 正式每日产品结果，是否已经在代码业务层完整形成？

### 8.2 必须验证

至少：

```text
trade_date
strategy run identity
strategy code / version
rule version set
parameter set
final target identity / digest
required provenance completeness
completion status
completed_at
```

### 8.3 Idempotency

同一业务版本与输入快照下重复执行：

- 不生成互相矛盾的两个 final product；
- 不覆盖其他历史版本；
- 能明确识别同结果重放；

### 8.4 Failure

以下任一情况 closeout 不得 SUCCESS：

```text
strategy result missing
formal target missing
target date mismatch
required provenance missing
version identity missing
target identity invalid
```
