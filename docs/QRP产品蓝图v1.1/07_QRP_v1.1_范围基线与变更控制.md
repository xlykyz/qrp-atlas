# QRP v1.1 范围基线与变更控制

> 本文件在蓝图 PR 合并后成为 v1.1 的范围管理规则。  
> 目的：允许研究继续产生新想法，但禁止新想法在实施过程中无控制地改变当前版本目标、边界和验收。  
> qrp-atlas 长期集成分支：`develop/v1.1`。

## 一、基线组成

v1.1 范围基线由以下文件共同组成：

1. `02_QRP_v1.1_产品终点.md`：产品范围说明；
2. `03_QRP_v1.1_数据与模块扩充规划.md`：模块、跨仓和技术边界；
3. `04_QRP_v1.1_开发路线图.md`：WBS、依赖、分支和里程碑；
4. `06_QRP_v1.1_总体验收清单.md`：验收标准；
5. `08_任务00_蓝图与规则治理封版.md`：交易规则基线；
6. 各任务文档：工作包字典。

蓝图合并后，任务执行者不得仅修改其中一份文件来改变范围；正式范围变更必须同步所有受影响基线。

## 二、范围内能力

v1.1 范围内：

- System B完整量化与生产版本；
- 市场判断和新开仓授权；
- 动态产业—题材库代码化；
- M1—M3核心身份；
- 历史全A和可交易性；
- eligibility、硬否决、评分、排名和完整目标组合；
- 全策略稳健性与系统验证；
- 每日运行产品与前端；
- qrp-atlas `execution`券商无关执行编排核心；
- 独立qrp-trading MiniQMT网关协议产品化；
- qrp-atlas MiniQMT gateway adapter；
- 跨服务调度、监控、恢复、仿真和小资金实盘验收。

## 三、范围外能力

v1.1明确不包含：

- System C；
- System A重新进入生产；
- short、借券、保证金；
- 多腿同步成交；
- 期货、期权；
- 高频、Level-2和订单簿预测；
- 强化学习；
- 分布式回测集群；
- 第三方SaaS交易平台；
- 多券商统一网关；
- 原生移动App；
- 任意Python策略上传；
- 盘中人工临时选股和下单入口；
- 将qrp-trading并入qrp-atlas；
- 在qrp-atlas中直接import xtquant。

范围外需求进入后续版本backlog，除非通过正式范围变更。

## 四、需求分类

新增想法必须先分类：

| 类型 | 定义 | 默认处理 |
|---|---|---|
| 缺陷 | 已批准能力未按基线工作 | 当前任务修复 |
| 澄清 | 不改变输入、输出和验收，只消除歧义 | 文档补充，可当前处理 |
| 参数变更 | 结构不变，仅调整阈值/权重/窗口 | 新parameter set，需验证 |
| 兼容性修复 | 保持既有行为和公共接口 | 当前任务必要修复 |
| 范围变更 | 增加/删除能力或改变验收 | 正式变更单 |
| 架构变更 | 改依赖、顶级模块、仓库或职责 | 正式变更单 + 架构评审 |
| 协议变更 | 改qrp-atlas与qrp-trading外部协议语义 | 版本化变更 + 双仓兼容评审 |
| 研究假设 | 需要数据验证、尚不进入生产 | research backlog |
| 后续版本需求 | 有价值但不属于v1.1 | v1.2+ backlog |

不得把范围变更描述为“顺手优化”“小补充”或“只加一个字段”绕过审批。

## 五、参数变化与规则变化

### 5.1 参数变化

满足以下条件时，可作为parameter set新版本：

- 输入字段不变；
- 状态集合不变；
- 规则关系不变；
- 优先级不变；
- 输出语义不变；
- 只改变阈值、权重、窗口、数量或开关。

### 5.2 规则/策略版本变化

出现以下任一情况必须新建规则或策略版本：

- 新增或删除输入；
- 新增状态；
- 改变状态转移；
- 改变硬否决；
- 改变规则优先级；
- 改变entry/hold/exit行为；
- 改变eligible与rank关系；
- 改变目标组合生成方式；
- 改变不可成交后的行为；
- 改变人工干预权限。

已发布版本不可原地修改。

### 5.3 网关协议变化

以下变化必须升级外部协议版本并更新兼容矩阵：

- 请求/响应字段删除或语义改变；
- 订单状态含义改变；
- 错误码含义改变；
- 幂等规则改变；
- WebSocket事件、sequence或恢复语义改变；
- 账户别名、权限或TRADE_ENABLED语义改变；
- 生产窄协议路径改变且不兼容。

新增向后兼容字段可在同一兼容版本内扩展，但必须测试旧客户端。

## 六、正式变更单

变更单至少包含：

```text
change_id
title
requester
requested_at
reason
current_baseline
proposed_change
business_value
in_scope / out_of_scope impact
data impact
contract impact
architecture impact
cross_repo impact
protocol impact
PIT impact
strategy behavior impact
backtest/replay impact
execution/gateway safety impact
test impact
schedule impact
risk
alternatives
recommendation
approval
```

审批结果：

- `APPROVED_CURRENT_RELEASE`：进入v1.1，更新基线和WBS；
- `APPROVED_FUTURE_RELEASE`：进入后续版本backlog；
- `RESEARCH_ONLY`：允许研究，不进入生产；
- `REJECTED`：记录原因，不执行；
- `DEFERRED`：等待信息，不进入当前任务。

## 七、变更审批门禁

以下变更必须由用户人工批准：

- 产品终点；
- System A/B/C定位；
- 判断层权限；
- 入场、退出、仓位和风险优先级；
- qrp-atlas顶级模块；
- execution与qrp-trading职责边界；
- qrp-trading是否独立部署/独立仓库；
- 生产数据源和题材canonical写入路径；
- 真实账户交易权限；
- MiniQMT下单、幂等和自动恢复策略；
- 通用RPC是否进入生产路径；
- 发布门禁和验收标准；
- v1.1工作包直接合入main。

Agent无权批准这些变更。

## 八、开发中发现缺口的处理

### 8.1 不改变范围的实现缺口

例如：

- 缺少必要索引；
- 现有函数不支持批量输入；
- 错误码不稳定；
- API缺少任务文档已要求的字段；
- 适配器缺少已批准协议映射；
- 网关缺少已批准的幂等持久化。

可在当前任务内解决，但必须：

- 与任务输出直接相关；
- 不增加新业务能力；
- 不改变公共语义；
- 增加测试；
- 在PR/验收报告中披露。

### 8.2 改变范围的产品缺口

例如：

- 临时决定增加盘中信号；
- 新增另一套策略；
- 加入机器学习模型；
- 改为支持多券商；
- 允许人工修改目标仓位；
- 把通用RPC直接当生产下单接口；
- 把qrp-trading数据库作为QRP业务SSOT。

必须暂停相关实现并提交变更单或进入backlog。

## 九、研究与生产隔离

研究可以：

- 测试新因子；
- 比较参数；
- 做替代规则回测；
- 分析错过和归因；
- 生成候选变更建议；
- 在隔离环境验证新网关能力。

研究不得：

- 自动改生产参数；
- 自动发布新策略版本；
- 自动修改canonical题材或角色；
- 在无审批时改变次日订单计划；
- 通过通用RPC绕过execution OMS；
- 以近期盈亏直接否定范围基线。

研究结论必须经过：

```text
research result
→ change proposal
→ independent validation
→ approval
→ new version
→ controlled rollout
```

## 十、分支与配置基线

### qrp-atlas

- `main`：稳定v1.0维护线；
- `develop/v1.1`：v1.1范围和工作包集成线；
- 工作包分支从`develop/v1.1`创建并回到该分支；
- `release/v1.1-acceptance`：最终冻结验收；
- 只有release分支向main提版本PR。

### qrp-trading

- 保持独立Git历史；
- 任务10-B锁定起始commit、交付commit、gateway version和protocol version；
- 跨仓验收报告同时引用两个仓库/工作区版本；
- 无远程仓库不等于可以不提交本地Git记录。

## 十一、基线状态

| 状态 | 含义 |
|---|---|
| DRAFT | 正在编写，尚未授权开发 |
| REVIEW | 等待评审 |
| BASELINED | 已批准，任务按此执行 |
| CHANGE_PENDING | 存在待审批变更 |
| SUPERSEDED | 被新基线替代，保留历史 |

本蓝图PR合并到`develop/v1.1`后，v1.1范围状态从`REVIEW`进入`BASELINED`；任务00规则基线仍需单独完成。

## 十二、与标准项目管理术语的映射

在标准项目管理语境中，本成果包不是单一文档，而是一组组合工件：

- 产品终点：产品愿景、产品范围描述和项目范围说明的组合；
- 能力矩阵：需求文档与需求跟踪矩阵的主体；
- 路线图：里程碑计划、依赖图和高层进度计划；
- 任务总表：工作分解结构（WBS）；
- 单个任务文档：WBS字典中的工作包定义；
- 总体验收清单：质量标准、验收标准和完成定义；
- 本文件：范围管理计划与变更控制规则；
- 各PR和跨仓commit：配置项变更、交付物评审和质量门禁载体，不是独立的项目管理基线。

当范围、WBS和WBS字典获得批准后，它们共同构成范围基线。时间和成本尚未估算并批准前，本蓝图不等于进度基线或成本基线。

## 十三、执行原则

> 渐进明细可以继续完善实现细节，但不得在范围基线之后用“渐进明细”无审批地改变产品终点、跨仓边界和工作包职责。

任何当前任务未要求的想法，默认进入backlog，而不是进入当前PR。
