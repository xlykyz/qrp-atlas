# 任务 10-A：QRP 执行编排核心

## 一、目标

在 `qrp-atlas` 内新增券商无关的 `execution` 顶级模块，将已经冻结的订单计划安全地转换为标准订单意图，并完成业务风险门、OMS、幂等、恢复、对账和 paper 执行核心。

本任务不 import `xtquant`，不直接连接 MiniQMT，不实现 Windows 网关生命周期，也不发送真实券商订单。

本任务回答：

> QRP 已经决定买什么、卖什么和目标数量之后，如何在不重复、不越权、可恢复、可对账的前提下管理业务订单生命周期。

## 二、前置

- 任务 01、07、09 已验收；
- 正式目标组合和订单计划契约稳定；
- 生产计划可冻结、取消和版本化；
- 任务 00 已冻结人工干预、未成交、退出和安全优先级；
- 独立 `qrp-trading` 网关被视为外部执行基础设施，不作为本任务内部模块。

## 三、系统边界

```text
strategies / portfolio target
             ↓
production order plan
             ↓
qrp-atlas/execution
  planning / business risk / OMS / recovery / reconciliation
             ↓  ExecutionGatewayProtocol
paper adapter 或 MiniQMT gateway adapter
             ↓
外部 qrp-trading（任务 10-B）
             ↓
MiniQMT / broker account
```

职责划分：

### qrp-atlas/execution 拥有

- 订单计划版本和冻结状态；
- 目标到订单差额计算；
- 业务风险门；
- `client_order_id`；
- 业务订单状态机；
- 订单与策略、目标、规则、参数的关联；
- paper 执行；
- 恢复和对账政策；
- QRP 业务审计。

### 外部 qrp-trading 拥有

- MiniQMT / xtquant 生命周期；
- 本机账户连接和订阅；
- REST / WebSocket；
- API Key、IP 白名单和网关级交易总开关；
- 原始券商请求、响应、回调和本地审计；
- QMT 连接与行情订阅恢复。

`execution` 不得把外部网关的通用 RPC 当作业务规则引擎，也不得让网关重新决定标的、方向、数量和策略优先级。

## 五、核心领域模型

至少实现：

```text
ExecutionAccount
AccountSnapshot
ExecutionPosition
FrozenOrderPlan
FrozenOrderPlanItem
OrderIntent
LiveOrder
OrderEvent
LiveFill
GatewayOrderReference
ExecutionControlState
ExecutionRun
ReconciliationResult
ReconciliationDifference
ManualIntervention
```

要求：

- 模型不得包含 xtquant SDK 对象；
- 网关原始 payload 只能以受控引用或脱敏快照保存；
- QRP `client_order_id` 与券商 `broker_order_id` 分离；
- 所有对象绑定 owner、账户别名、业务日期和时区；
- 订单必须关联 strategy decision、portfolio target 和 plan item；
- 状态、枚举和 reason code 稳定可序列化。

## 六、ExecutionGatewayProtocol

定义面向外部执行网关的稳定协议：

```text
health()
capabilities()
list_accounts()
query_account(account_alias)
query_positions(account_alias)
query_orders(account_alias)
query_fills(account_alias)
submit_order(StandardOrderCommand)
cancel_order(StandardCancelCommand)
subscribe_events(handler)
```

协议不包含：

```text
connect
disconnect
start
stop
register_callback
run_forever
```

这些生命周期由外部网关统一维护，不允许 QRP 任意远程破坏。

协议要求：

- 支持 paper 和远程网关两种实现；
- 核心 service 只依赖标准协议；
- 查询、提交、取消和事件有明确超时与错误语义；
- 支持能力协商和协议版本；
- 不允许 SDK 类型穿透协议；
- 网关未知结果必须映射为显式 UNKNOWN，而非猜测成功或失败。

## 七、订单计划到订单意图

转换过程：

```text
frozen order plan
+ latest account snapshot
+ latest broker positions
+ active orders
→ target/current delta
→ deterministic quantity normalization
→ business risk gates
→ order intents
```

要求：

- 计划版本不可变；
- 使用最新账户事实验证，但不反向修改策略目标；
- 账户或持仓差异超限时阻塞并要求重新生成计划；
- BUY/SELL、数量和优先级确定性；
- A 股整数手、可用数量和特殊退出规则明确；
- 同日退出和入场顺序遵循任务 00；
- 所有 intent 绑定 source plan item；
- 不因网关返回或盘中价格变化重新评分候选。

## 八、业务风险门

### 8.1 系统门

- execution enabled；
- control state；
- kill switch；
- 正确交易日和执行时段；
- production run 与计划已成功冻结；
- 数据、计划和账户快照未过期；
- adapter health 与协议版本兼容；
- recovery/reconciliation 已通过。

### 8.2 账户门

- owner 和账户别名匹配；
- 可用资金；
- 当前持仓与可用数量；
- 单票和总暴露；
- 题材集中度；
- 当日新增风险；
- 订单数量和金额上限；
- 目标与现实账户差异；
- 非计划外人工持仓和活动订单。

### 8.3 订单门

- asset、side、quantity、price type 合法；
- 幂等键未被完成或占用；
- 无冲突活动订单；
- 不重复卖出超过可用数量；
- 不重复买入已满足目标；
- 计划未取消、过期或被替代；
- 标的和交易时段符合已批准计划。

风险门 fail closed，并输出稳定 reason code。网关自身的 API Key、IP、`TRADE_ENABLED` 等机械安全门是第二道防线，不能替代 QRP 业务风险门。

## 九、幂等与请求身份

`client_order_id` 必须由稳定业务身份生成，例如：

```text
owner/account + plan_id + plan_item_id + attempt_generation
```

另定义每次远程调用的 `request_id`。

要求：

- 重复执行同一计划不重复发送；
- 同一 `request_id` 的重试得到相同或可恢复结果；
- submit 超时后先查询网关/券商，不盲目重发；
- broker order id 返回后建立唯一映射；
- 未知结果进入 `UNKNOWN`；
- 只有正式新 attempt generation 才允许再次提交；
- generation 增加必须有明确业务原因和审计；
- 幂等状态跨进程和重启持久化。

## 十、订单状态机

至少支持：

```text
PLANNED
VALIDATED
BLOCKED
SUBMITTING
SUBMITTED
PARTIALLY_FILLED
FILLED
CANCEL_PENDING
CANCELLED
REJECTED
EXPIRED
UNKNOWN
```

要求：

- 每次迁移有事件、时间、来源、request_id 和原始证据引用；
- 非法迁移拒绝；
- REST 返回、WebSocket 回调和主动查询都可产生标准事件；
- 回调可乱序、延迟和重复，处理必须幂等；
- 部分成交数量累计不可超过订单数量；
- 终态不可被旧事件回退；
- `UNKNOWN` 不等价 `REJECTED`；
- 网关状态与业务状态分离保存；
- 协议新增未知状态时 fail closed 并进入诊断。

## 十一、paper adapter

实现 broker-neutral paper adapter：

- 不连接真实账户；
- 使用明确价格和成交规则；
- 可模拟全部成交、部分成交、拒单、延迟、断线和重复事件；
- 实现与远程网关相同的 `ExecutionGatewayProtocol`；
- 复用相同 OMS、风险门、store、recovery 和 reconciliation；
- 不以历史回测引擎替代 live OMS 测试；
- paper 账户和正式账户配置严格隔离。

## 十二、持久化

必须原子保存：

- execution control state；
- 计划执行状态；
- order intents；
- live orders；
- order events；
- fills；
- account/position snapshots；
- gateway/broker mappings；
- request idempotency；
- reconciliation；
- manual interventions。

支持：

- 跨进程锁；
- 崩溃恢复；
- 重复启动；
- owner/account 隔离；
- 事件追加或等价不可丢失审计；
- 原子提交与备份恢复。

## 十三、恢复

启动顺序：

```text
load local state
→ initialize adapter
→ health/capability negotiation
→ query account/positions/orders/fills
→ match gateway and broker references
→ replay missing events
→ reconcile
→ resolve UNKNOWN where possible
→ enable new submissions only after recovery gate
```

恢复期间禁止发送新订单。

外部网关重启、QMT 重连或 WebSocket 中断后，也必须先主动查询和对账，再恢复新增提交。

## 十四、对账核心

比较：

- 策略目标组合；
- 冻结订单计划；
- QRP 本地业务订单和成交；
- qrp-trading 网关审计/查询事实；
- 券商委托、成交、持仓和资金。

差异分类至少包括：

```text
MISSING_LOCAL_ORDER
MISSING_GATEWAY_REQUEST
MISSING_BROKER_ORDER
ORDER_STATUS_MISMATCH
FILL_MISMATCH
POSITION_MISMATCH
CASH_MISMATCH
EXTERNAL_MANUAL_TRADE
UNKNOWN_ASSET
STALE_SNAPSHOT
PROTOCOL_VERSION_MISMATCH
```

原则：

- 券商事实优先确认订单和成交现实；
- QRP 保存业务原因和目标权威；
- qrp-trading 保存原始请求/响应/事件证据；
- 差异不可通过覆盖本地数据自动消除；
- 未解释差异阻塞新增提交或进入人工处理队列。

## 十五、人工控制

允许的制度化控制：

- enable/disable execution；
- pause new submissions；
- cancel pending plan；
- cancel active order（经权限和审计）；
- kill switch；
- 对账差异处置；
- 明确的新 attempt generation。

不得提供：

- 盘中临时增加标的；
- 修改策略分数或排名；
- 绕过硬否决；
- 直接调用网关通用 RPC 下任意订单；
- 修改已冻结目标仓位。

## 十六、QRP API

只暴露标准 execution API：

- control state；
- plans、intents、orders、fills；
- execute frozen plan；
- cancel order/plan；
- reconciliation；
- recovery status；
- adapter health/capabilities；
- audit。

真实 MiniQMT 网关适配在任务 10-B 注册。前端不接触网关 API Key、SDK 参数和通用 RPC。
