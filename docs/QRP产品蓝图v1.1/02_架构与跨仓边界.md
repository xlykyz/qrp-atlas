# 架构与跨仓边界

> **2026-09-04 中期评估调整**：本文件保留早期 execution / qrp-trading 架构设计，但这些能力已退出 QRP v1.1 Core 当前范围。调整属于语义与产品身份治理，不要求对已有代码做大规模物理重构。System B 可继续作为 QRP 内置策略开发；内置与外部插入能力原则上复用同一套 contracts、registry、pipeline、database、runtime 与 result 基础设施。
>
> 原因：① QRP Core 定位收敛为历史数据、PIT 数据生产、指标计算、策略运行、量化分析、回测、重放与每日策略产品；② 原计划依赖的 MiniQMT 实盘交易路径自 2026 年 9 月起面临券商侧陆续关闭接口的现实约束。未来实盘能力如恢复，应作为独立 Execution Extension 或后续版本能力，不再作为 v1.1 发布前提。

## 1. 核心依赖方向

QRP v1.1 继续保持事实、指标与决策分层，并在 Task 04 引入正式的股票集合领域：

```text
contracts → stock_collections → indicators → strategies
```

这里描述的是业务信息流与职责边界，不要求 `indicators` 为了形式统一直接 import `stock_collections`。`stock_collections` 负责把集合身份和 PIT 成员关系解析为准备好的标准输入；`indicators` 继续保持纯计算，不负责数据库访问或 PIT 版本选择。

v1.1 Core 当前产品链收敛为：

```text
pipeline
→ contracts
→ stock_collections
→ indicators
→ strategies
→ portfolio target
→ production run / replay / result
```

早期 execution 扩展链保留如下，不再属于 v1.1 Core：

- ~~→ execution~~
- ~~→ gateway adapter~~
- ~~→ qrp-trading~~

底层不得反向依赖上层；通用回测引擎不得包含 System B、题材、五日线或具体业务规则知识。

## 2. qrp-atlas 模块职责

### contracts

定义标准字段、领域对象、持久化表、主键、PIT 时间语义、版本和 owner 语义。

### pipeline

采集、清洗、标准化、版本化和读取市场及研究事实，不生成策略动作。

### stock_collections

`qrp_atlas.stock_collections` 是 v1.1 正式顶级领域，负责股票集合的标准化身份与 PIT 成员解析，包括：

- stable collection identity 与 registry；
- collection lifecycle；
- 原生成员事实的领域持久化与 repository 边界；
- PIT membership resolution；
- asset → collections 反向查询；
- membership provenance / explainability。

持久化字段、表结构、主键和 PIT 字段语义仍由 `contracts` 定义；`stock_collections` 不建立第二套 schema SSOT。

Task 04-A 当前生产实现范围仅为：

```text
collection_type = THEME
member asset domain = EQUITY
```

`INDUSTRY`、`INDEX`、`SYSTEM_POOL`、`USER_DEFINED`、`RESEARCH` 等类型可以保留为已批准的设计空间，但本阶段不得提前实现其 Adapter、Repository 或生产路径，也不建设通用 Asset Domain。

`stock_collections` 不负责：

- 外部数据采集与 provider 接入；
- Theme 等权指数；
- MA5 / MA10、趋势状态或 Episode；
- M4、M5、M6 指标计算；
- 评分、策略判断或交易授权。

Theme Membership 与 M4 计算资格必须分离。上市实际交易日数 `<= 5` 或观察日停牌只影响后续 M4 计算资格，不得改变 Theme Membership。

### indicators

计算客观状态与事实，包括：

- 基础趋势状态；
- 行情轮次；
- 涨停状态池；
- 容量、高度和辨识度事实；
- 题材等权指数与题材指标；
- M4、M5、M6 所需客观观察；
- 严重异动事实与监管状态。

`indicators` 消费调用方已经准备好的标准数据或 StockCollection 成员结果，不主动查询数据库，不负责 PIT membership selection。指标不输出 ENTER、EXIT 或目标仓位。

### strategies

消费已准备的事实，输出：

- 新增仓授权结果；
- eligible / veto / score / rank；
- ENTER / HOLD / EXIT / NO_ACTION；
- 完整目标组合。

评分公式未冻结前，只实现稳定接口、显式缺失状态和可插拔版本，不得暗置权重。

产品身份上，策略应区分“语义归属”和“交付方式”：

```text
semantic_owner = QRP_CORE / SYSTEM_B / OTHER_USER

delivery_mode = BUILTIN / PLUGIN / EXTERNAL
```

System B 当前可以继续采用：

```text
semantic_owner = SYSTEM_B
delivery_mode = BUILTIN
```

这表示其业务规则语义来源于 MyTradingSystem/System B，但作为 QRP bundled built-in strategy 随项目开发、测试与发布。该身份不要求建立第二套 pipeline、database、registry 或 runtime。

### backtest

负责数据准备、历史运行、现实成交模拟、组合资金、T+1、停牌、涨跌停、整数手、成本、持仓和绩效评价。

### production product

负责每日运行状态机、输入快照、阶段产物、失败恢复、结果查询和审计。

### execution

- ~~负责目标之后的业务风险；~~
- ~~订单计划；~~
- ~~order intent；~~
- ~~OMS 状态；~~
- ~~幂等；~~
- ~~撤单与恢复；~~

## 6. 回测与实盘一致性

v1.1 当前要求一致的部分：

- 规则版本；
- 参数版本；
- 输入事实；
- eligible / score / rank；
- 策略决定；
- 目标组合；
- 历史回放与每日运行中的结果语义。

早期实盘一致性设计保留如下，不再属于 v1.1 当前验收：

- ~~订单计划语义；~~
- ~~实盘由 execution + qrp-trading + 券商执行；~~
- ~~券商事件、网络失败、幂等恢复和对账只属于实盘链。~~

回测继续由通用执行引擎模拟；该模拟能力用于研究与验证，不意味着 QRP Core 必须拥有真实券商交易能力。
