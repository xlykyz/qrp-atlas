# QRP 产品蓝图 v1.1

> **文档状态：产品终点与实施范围基线草案，等待本 PR 验收**  
> **形成日期：2026-07-22**  
> **审计基线：main `a307e58e138677cadcc38a0da2148639b1f99a5c`**  
> **v1.1 集成分支：`develop/v1.1`**

## 一、本成果包的作用

`docs/QRP产品蓝图v1.0/` 已经完成量化研究平台的后端产品闭环，回答了：

> 标准数据、指标、策略、组合回测、结果、API 与前端如何形成可复现的研究产品。

本成果包继续回答：

> 如何把用户现行交易系统完整翻译为可计算、可回测、可审计、可每日运行，并通过独立 MiniQMT 网关执行的生产系统。

本蓝图不是先做一个最小版本再临时追加规则，而是先冻结完整终点、模块边界、工作分解结构、依赖和验收标准，再按任务包逐步交付。

## 二、v1.1 的唯一主线

```text
全市场与外部信息更新
→ 市场状态与策略授权
→ 动态产业—题材周期
→ M1/M2/M3 核心身份
→ System B 全市场趋势状态
→ 资格与硬否决
→ 评分、排序与目标组合
→ 次日订单计划
→ qrp-atlas/execution 执行编排与业务风控
→ qrp-trading MiniQMT 网关
→ 成交、持仓与账户对账
→ 日结、复盘、归因与回放
```

生产策略范围：

- `System B`：v1.1 唯一实盘生产策略主线；
- 判断层：只决定新开仓授权，不接管既有持仓退出；
- `System A`：标记为 `LEGACY`，保留历史研究与归因，不进入实盘授权链；
- `System C`：不属于 v1.1；
- 第一性原理、时间约束和规则版本：属于治理与审计层，不直接生成单笔交易信号。

## 三、受控架构扩展

v1.0 的核心量化抽象继续保持：

```text
contracts → indicators → strategies
```

v1.1 在 `qrp-atlas` 中增加一个受控顶级模块：

```text
execution
```

`execution` 负责策略之后、券商调用之前和之后的业务执行编排，包括订单计划转换、业务风险门、OMS、幂等、恢复、对账和网关适配；它不直接 import `xtquant`。

独立本地仓库 `qrp-trading` 定位为 Windows MiniQMT 边缘网关，负责：

- MiniQMT / xtquant 生命周期与单例连接；
- 账户发现、订阅、查询、下单、撤单和事件转发；
- REST / WebSocket、API Key、IP 白名单、脱敏和网关审计；
- QMT 断线恢复和本机能力发现；
- `TRADE_ENABLED` 等网关级机械安全门。

二者通过版本化 HTTP / WebSocket 协议连接，不共享数据库：

```text
qrp-atlas/execution
        │  frozen plan / standard commands / client_order_id
        ▼
qrp-trading
        │  MiniQMT / xtquant
        ▼
broker account
```

边界约束：

- `strategies` 不得直接调用 `execution`、`qrp-trading` 或 `xtquant`；
- `execution` 不得重新计算指标、资格、评分和目标组合；
- `qrp-trading` 不得决定交易标的、方向、数量、策略授权或目标仓位；
- QMT SDK 类型不得穿透 qrp-trading 的外部协议进入 QRP 核心；
- 通用 RPC 只作为受控管理/诊断能力，生产下单必须使用封板的窄协议；
- qrp-trading 的 `audit.db` 是网关原始证据账本，QRP 数据库是业务订单权威账本，券商账户是最终现实事实。

## 四、分支治理

QRP v1.1 使用长期集成分支：

```text
main                       稳定 v1.0 维护线
└── develop/v1.1           v1.1 长期集成线
    ├── feat/v1.1-wp00-...
    ├── feat/v1.1-wp01-...
    └── ...
         └── release/v1.1-acceptance
                 └── PR → main → tag v1.1.0
```

规则：

- 所有 v1.1 工作包从 `develop/v1.1` 创建分支，并向 `develop/v1.1` 提 PR；
- 工作包不得直接向 `main` 提 PR；
- `main` 仅接受 v1.0 严重缺陷、安全和生产阻塞修复；
- main 修复通过普通 merge 同步到 `develop/v1.1`，禁止长期集成分支 rebase/force push；
- 全部工作包完成后，从 `develop/v1.1` 创建 `release/v1.1-acceptance`；
- 验收分支只允许验收修复，最终以版本级 PR 合入 `main`。

## 六、状态标记

| 标记 | 含义 |

## 七、使用方式

1. 先读 [01](./01_QRP_v1.1_当前能力审计与能力矩阵.md) 确认地基和缺口；
2. 用 [02](./02_QRP_v1.1_产品终点.md) 判断需求是否属于 v1.1；
3. 用 [07](./07_QRP_v1.1_范围基线与变更控制.md) 处理新增想法和规则变更；
4. 严格按 [04](./04_QRP_v1.1_开发路线图.md) 和 [05](./05_QRP_v1.1_Agent任务包.md) 逐包执行；
5. 每个任务完成后同步能力矩阵和 [06](./06_QRP_v1.1_总体验收清单.md)；
6. 未经人工验收，不得跨任务提前宣称 v1.1 可实盘运行。

## 八、蓝图封版含义

蓝图合并只表示：

- 产品终点、范围、模块、跨仓边界和工作包获得批准；
- 可以按已批准顺序开始实现；
- 新想法必须通过变更控制进入后续版本或正式变更单。

它不表示任何 v1.1 运行能力已经完成，也不授权实盘下单。
