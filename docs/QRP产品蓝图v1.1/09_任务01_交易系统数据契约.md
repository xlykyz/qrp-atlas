# 任务 01：交易系统数据契约

## 一、目标

把任务 00 已批准的规则、参数和产品输出翻译为正式 contracts、领域模型、主键、时间语义、版本语义和持久化边界。

本任务只定义“数据是什么”，不计算指标、不生成交易动作、不实现 QMT。

## 二、前置

- 任务 00 已验收；
- 初始规则版本集和参数集已冻结；
- v1.1 范围基线已生效。

## 四、时间语义

每类对象按适用范围明确：

```text
business_date
trade_date
event_time
published_at
available_at
available_trade_date
observed_at
ingested_at
effective_from / effective_to
valid_from / valid_to
created_at
```

要求：

- `created_at` 不替代市场可用时间；
- 事实有效时间与 QRP 认可时间分离；
- 决策和目标保存当时输入快照；
- live order 时间使用 timezone-aware 时间戳；
- 交易日标签与事件时间分离；
- 所有时区显式，A 股业务默认 Asia/Shanghai。

## 五、身份与主键

必须定义稳定身份：

- rule/version/set；
- theme/version/cycle；
- membership/role observation；
- production run；
- target snapshot；
- order plan；
- client order；
- broker order；
- fill；
- reconciliation difference。

`client_order_id` 必须可用于幂等，不得直接使用券商 order_id 作为内部主键。

## 六、状态枚举

至少定义：

- 规则状态；
- 市场阶段；
- 策略授权状态；
- System B 生命周期；
- 资格结果；
- 题材生命周期；
- 角色类型；
- production run/stage 状态；
- order plan 状态；
- live order 状态；
- reconciliation 状态；
- trading control 状态。

枚举值必须稳定、可序列化、禁止把 Python Enum repr 写入 API 或存储。

## 七、owner 与权限

- canonical 市场、题材和派生事实按产品共享；
- 私有研究笔记、订阅、草稿、agent run 和未提交 proposal 带 `owner_id`；
- 生产运行、订单计划、账户、订单、成交和对账全部带 owner/account 边界；
- 不能仅凭可猜测 ID 访问其他 owner 数据；
- 账户敏感标识在 API 中最小化展示。

## 八、兼容与迁移

- 旧 `market_phase` 保留只读兼容，不继续加字段；
- 旧 `trade_execution` 保留历史查询，不作为 OMS；
- `system_b_basic@1.0.0` 和旧结果继续可读；
- 新 contracts 先增加，再迁移生产者和消费者；
- 提供 migration、schema audit、backup 和 rollback；
- 不通过静默 nullable 放宽解决不一致。

## 九、公开接口

contracts 必须公开：

- 字段常量；
- TableSchema / domain model；
- 枚举；
- schema 对齐和校验；
- 时间规范化；
- 身份生成规则；
- 序列化/反序列化；
- 兼容映射。

## 十、测试

至少覆盖：

- 主键和不可空；
- 枚举稳定值；
- schema 对齐；
- 时间和时区；
- PIT 字段；
- owner 边界；
- 版本不可变；
- 幂等 ID；
- 旧表兼容；
- migration noop/repeat/rollback；
- 非法状态转移和缺失字段拒绝。

## 十一、禁止范围

- 不实现指标计算；
- 不实现判断层；
- 不实现策略；
- 不实现 QMT；
- 不创建第二套字段常量；
- 不修改已批准规则；
- 不用 JSON 大字段代替应正式建模的核心身份和状态。

## 十二、验收

- contracts 成为 v1.1 全部生产对象 SSOT；
- 所有后续任务所需输入输出均有正式契约；
- 时间、版本、owner 和幂等语义完整；
- migration 和兼容测试通过；
- 全量测试和静态检查通过；
- 文档和能力矩阵同步；
- PR 等待独立验收。
