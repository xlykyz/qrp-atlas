一、总评

结论：有救，而且底子比预期好

这个项目的架构决策质量远高于代码实现质量。数据契约层 (contracts/) 的设计、pipeline 的分源独立、回测引擎的解耦，这些是在很多商业项目里都看不到的正面模式。真正拖低项目体验的是三类"成长痛"：前端组件膨胀、工具函数迁移未完成、后端依赖清理滞后——全部是 1-2 周内可修复的表层债务，不涉及架构推翻。

不建议重写。建议按四阶段渐进式重构，每个阶段完成后项目都可正常上线。

三、逐层诊断

3.1 contracts/ 数据契约层 资产

这是整个项目最亮眼的模块。使用 frozen dataclass 定义 ColumnSpec 和 TableSchema，12 张表的列规格、主键、DuckDB 建表 SQL 全部集中在一个文件里，是真正的 SSOT（Single Source of Truth）。

检查项状态说明
字段常量化GOODfields.py 统一定义，避免魔法字符串
表结构声明式GOODfrozen dataclass，不可变，可哈希
建表 SQL 自动生成GOODduckdb_create_sql() 方法，支持单列/多列主键
入库前校验GOODvalidate.py 做 schema 对齐 + 类型转换
外部字段映射GOODmappings.py 集中管理多数据源字段映射
A 股规则封装GOODconventions.py 封装 ticker 规范化、板块识别等
诊断意见
contracts/ 层设计成熟，是项目的核心资产。唯一建议：schema.py 目前 463 行，12 张表全在一个文件里，后续表数增长时可考虑按业务域拆分（如 market / research / trade）。

3.2 pipeline/ 数据管线 资产

4 条正式管线各自独立，每条都遵循 fetch → clean → load 三段式，结构清晰。daily_update 管线还支持 enrich 阶段和从 raw 重跑的模式。

检查项状态说明

raw 数据保存GOODsave_raw_snapshot 保留原始数据，可回溯
canonical 数据保存GOOD清洗后数据落 CSV，可审计
批量重跑支持GOODreprocess_from_raw 支持批量模式 + 共享连接

日志规范DEBT全部用 print()，无 logging 模块，无结构化日志

3.3.3 查询参数安全

路由层的查询参数普遍使用了参数化查询（? 占位符 + params 列表），这是正确的做法。但 daily.py 的单日查询分支使用了较复杂的窗口函数 SQL，拼接逻辑较多，虽然参数本身是安全的，但 SQL 字符串可读性差，后续维护成本高。

3.3.4 DuckDB 连接管理

所有路由都使用 try/finally + con.close() 模式，确保连接释放。但每个请求都新建一个 DuckDB 连接，在高并发场景下会有性能问题。DuckDB 的推荐用法是共享一个只读连接（读操作不需要每次新建连接）。

3.4 backtest/ 回测引擎 半成品

引擎的架构设计是干净的：engine 编排、broker 撮合、metrics 统计、validators 校验，各自职责明确。但有一个关键功能缺失。

检查项状态说明
引擎无状态GOODBacktestEngine 可重复调用 run()
撮合逻辑完整GOOD支持 signal_close / next_open / next_close 入场，hold_n_bars 出场，含成本计算
MAE/MFE 计算GOOD正确使用 high/low 窗口计算最大不利/有利偏移
Skipped 原因分类GOOD7 种跳过原因常量化，便于诊断信号失败原因
metrics 汇总GOOD胜率/盈亏比/MAE/MFE 均值等指标齐全
equity_curveBAD始终返回空数组 []，净值曲线功能未实现
只支持 longDEBTv0.1 限制，可接受但需文档标注
# engine.py:71-77 — equity_curve 始终为空
return BacktestResult(
    config=config,
    summary=summarize_trades(trades, skipped),
    trades=trades,
    skipped=skipped,

诊断意见
equity_curve 是回测引擎的核心交付物之一（净值曲线），目前完全缺失。前端 backtest-analysis.tsx 如果依赖此字段渲染图表，会显示空白。这是回测功能的最高优先级补全项。

五、重构方案

核心原则：不推翻重来，每个阶段完成后项目可正常上线。

1
止血 — 消除重复与残留
1-2 天
  • 删除重复工具函数：overview.tsx 和 stock-review.tsx 删掉本地 formatPct/pctColor/formatAmount/formatVolume，改用 import { formatPct, pctColor, ... } from '@/shared/lib/format'
  • 清理依赖：pyproject.toml 删除 streamlit、plotly；fastapi 从 optional-dependencies.test 中去重
  • SQL 注入修复：server.py stats() 用白名单（TABLE_BY_NAME 的 keys）替代 f-string 拼接
  • CORS 收紧：allow_origins 从 ["*"] 改为具体前端地址（或至少去掉 allow_credentials=True）
影响：零风险，纯清理，项目立刻变干净。lint 和 build 不受影响。
2
拆分 — 前端组件解耦 + API 类型化
3-5 天
  • stock-review.tsx 拆分（2,140 行 → 5-6 个文件）：
    • hooks/useStockData.ts — 数据获取 + 状态管理
    • components/StockChart.tsx — K 线图渲染
    • components/TradeForm.tsx — 交易记录表单
    • components/PhaseMarker.tsx — 阶段标记
    • components/ResearchPanel.tsx — 研报列表
    • pages/stock-review.tsx — 页面组装（<150 行）
  • overview.tsx 拆分（596 行 → 3 个文件）：
    • hooks/useDailyData.ts — 日期锚定 + 数据获取
    • components/KpiCards.tsx — KPI 卡片
    • components/StockTable.tsx — 表格 + 排序 + 分页
  • API Pydantic model 补全：stock.py 等路由加 response_model，OpenAPI schema 自动完整
  • 前端类型同步：用 openapi-typescript 从 /docs/schema.json 生成前端 TS 类型
影响：体验改善最大的一步。代码可维护性从"改一行要找半天"变成"各司其职"。
3
加固 — 测试 + 容错 + 核心功能补全
1-2 周
  • 补 equity_curve：backtest engine 按交易时间序列计算累计净值，返回 List[dict] 而非 []
  • pipeline 测试：给 daily_update 的 clean + load 补单元测试，用固定 CSV 输入验证输出
  • contracts.validate 测试：覆盖正常/异常 DataFrame 输入，确保入库前校验生效
  • 前端 ErrorBoundary：App 层包裹 ErrorBoundary，单页崩溃时显示降级 UI 而非白屏
  • 数据请求层统一：封装 useApi hook，统一 loading / error / retry 状态管理
  • 依赖锁版本：pip freeze 生成 requirements.lock 或迁移到 uv/pdm
影响：项目从"能跑"变成"可信赖"。回测引擎完整可用，数据入库有测试保障。
4

持续

影响：从个人项目进化为可持续维护的系统。

六、总结

一句话诊断

架构设计 8.5 分，代码实现 6 分——骨架是优秀的，肉需要长。

这个项目不需要推翻重来。contracts 数据契约层、pipeline 分源独立、backtest 引擎解耦，这三个架构决策比大部分个人项目都好。真正的问题是前端组件膨胀（stock-review.tsx 2,140 行）、工具函数迁移未完成（3 个页面重复定义 shared/lib 里已有的函数）、后端依赖清理滞后（streamlit/plotly 残留）、测试严重不足（7/74 文件覆盖）、回测引擎核心功能缺失（equity_curve 永远为空）。

按 Phase 1→2→3→4 走，1-2 天止血，1 周拆分，2 周加固，持续进化。每个阶段完成后项目都可正常上线，不存在"重构到一半没法用"的中间态。
