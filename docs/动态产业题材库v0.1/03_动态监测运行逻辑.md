# 动态产业-题材库：动态监测运行逻辑

> 原则：确定性数据管道负责事实和分数，规则/统计模型负责变化检测，AI 负责检索与解释。三者不得互相冒充。

## 1. 运行目标

监测系统持续回答四件事：

1. 是否出现了新的候选题材或催化？
2. 已有题材的市场强度、扩散、拥挤和证据是否发生实质变化？
3. 哪些公司与题材的关系新增、减弱、冲突或失效？
4. 哪些变化值得通知，哪些只应进入盘后摘要或审核队列？

输出是结构化变化事件，不是自然语言新闻流：

```text
ThemeChangeEvent
├── what：变化类型与前后值
├── why：触发规则和贡献项
├── evidence：来源与市场事实
├── confidence：覆盖率与置信度
├── severity：通知等级
└── lineage：运行批次、版本和 as-of
```

## 2. 分层运行架构

```text
来源采集
  → 原始快照与内容哈希
  → 标准化实体 / 事件 / 来源关系
  → 实体解析与日快照差分
  → 派生指标计算
  → 变化检测与生命周期状态机
  → 告警聚合、去重和路由
  → 摘要 / 审核队列 / API
  → Agent 解释（按需、可降级）
```

每层写入独立输出和运行状态。上游失败时下游不得把“无数据”解释为“无变化”。

## 3. 输入信号

### 3.1 事件与证据信号

| 信号 | 例子 | 默认可靠性 |
| --- | --- | --- |
| P0 官方一手 | 监管政策、公司公告、交易所互动、公司官网 | 高 |
| P1 授权结构化 | 供应商题材/成员、板块行情、热榜 | 中高，保留供应商口径 |
| P2 专业二手 | 券商研报、通讯社、权威媒体 | 中，需要来源独立性判断 |
| P3 市场/社区 | 搜索、人气、社区讨论、社媒 | 低到中，只用于注意力 |

证据支持的主张类型限定为枚举，例如：`has_product`、`has_capacity`、`has_order`、`customer_exposure`、`supply_relation`、`price_change`、`policy_benefit`、`denial`。自由文本只能补充说明，不能代替主张类型。

### 3.2 市场信号

- 题材/概念指数收益、成交额、换手、振幅；
- 成员上涨占比、创新高占比、涨停/连板/炸板数量；
- 等权与市值加权收益差、核心与跟随分化；
- 主力净流入等供应商字段（单独标注口径）；
- 热榜、人气和搜索变化；
- 成员与市场/行业基准的残差收益；
- 数据覆盖率、停牌和涨跌停可交易性。

### 3.3 结构变化信号

- 供应商新增/删除题材；
- 供应商成员日快照差分；
- 新别名、同义题材和潜在合并；
- 公司角色变化、证据过期或出现反证；
- 产业链节点新增、供需方向改变；
- 题材覆盖的行业集中度变化。

## 4. 指标体系

所有分数归一到 `[0, 100]`，同时返回 `coverage`、`components` 和 `calculation_version`。缺失不按 0 处理。

### 4.1 一级指标

| 指标 | 含义 | 主要输入 |
| --- | --- | --- |
| `catalyst_score` | 催化的新鲜度、可靠性和影响范围 | 事件级别、来源、时间衰减、独立来源数 |
| `attention_score` | 市场关注变化 | 热榜、搜索、新闻量、互动量的稳健 z-score |
| `strength_score` | 价格与成交强度 | 超额收益、成交额、涨停、连板、残差收益 |
| `breadth_score` | 强势是否从少数核心扩散 | 上涨占比、创新高占比、涨停覆盖、等权表现 |
| `leadership_score` | 核心标的持续性 | 核心排名稳定、领涨贡献、开板/回撤 |
| `capital_score` | 资金参与程度 | 成交额增量、换手、授权资金流字段 |
| `evidence_score` | 业务关系可信度 | 高等级证据覆盖、独立来源、反证、时效 |
| `novelty_score` | 相对近期基线的新颖程度 | 新事件、新成员、新词、历史相似度 |
| `crowding_score` | 过热和一致性风险 | 换手极值、连板集中、核心贡献集中、人气极值 |
| `risk_score` | 逻辑和交易风险 | 反证、澄清、减持、监管、退潮、数据缺口 |

### 4.2 综合分数

MVP 的 `theme_activity_score` 用于排序，不用于收益预测：

```text
activity =
  0.16 * catalyst
+ 0.14 * attention
+ 0.18 * strength
+ 0.14 * breadth
+ 0.10 * leadership
+ 0.08 * capital
+ 0.12 * evidence
+ 0.08 * novelty
```

风险不简单从 activity 相减，而是并列展示：高活跃与高拥挤可以同时成立。

计算约束：

- 权重配置版本化；
- 覆盖率低于 60% 时不输出综合分数，只输出可用组件；
- 任一供应商黑盒分数权重不得超过综合分数的 20%；
- winsorize、z-score 和基线窗口参数进入版本；
- 按题材规模分组或做规模中性，避免成员多的题材天然占优；
- 日频与盘中使用不同基线，不直接比较绝对值。

### 4.3 成员双轴分数

业务相关度：

```text
business_relevance =
  0.30 * evidence_quality
+ 0.25 * revenue_or_capacity_exposure
+ 0.20 * chain_role_criticality
+ 0.15 * evidence_freshness
+ 0.10 * source_independence
- contradiction_penalty
```

市场共振度：

```text
market_resonance =
  0.30 * residual_return
+ 0.20 * volume_expansion
+ 0.20 * co_movement
+ 0.15 * leadership_persistence
+ 0.15 * attention
```

当营收/产能暴露未知时，业务相关度必须降低 coverage，而不是假设为 0。

## 5. 生命周期状态机

### 5.1 状态定义

| 状态 | 必要条件示例 | 产品解释 |
| --- | --- | --- |
| `candidate` 候选 | 新事件/新词/供应商新增，证据或市场确认不足 | 等待去重和验证 |
| `emerging` 萌芽 | 催化/新颖度高，至少一项市场确认，证据覆盖达门槛 | 新叙事开始形成 |
| `active` 活跃 | 活跃分持续高于分位阈值，扩散与核心至少一项稳定 | 已形成可观察主线 |
| `accelerating` 加速 | 活跃分一阶变化显著为正，扩散增加且非单票驱动 | 共识快速扩张 |
| `diverging` 分歧 | 强度仍高但扩散/核心持续性下降，拥挤或风险上升 | 高波动与内部背离 |
| `cooling` 退潮 | 活跃分跌破阈值，注意力与扩散同步下降 | 叙事降温 |
| `dormant` 沉寂 | 连续 N 日低活跃且无新催化 | 保留历史，不进入默认榜单 |

市场生命周期状态机**不包含** `reactivated` / `archived`：

- “复燃”创建新的 `theme_cycle`（`previous_cycle_id` 指向旧周期），新周期从 `candidate/emerging` 起步；
- “归档、合并、错误实体”写入 `theme.record_status`，不进入状态机。

### 5.2 迁移约束

- 状态迁移至少需要两个独立信号维度，避免单一涨停或单条新闻触发“活跃”；
- `candidate → emerging` 必须满足最小证据或来源等级；
- 从 `dormant` 再次启动必须有独立新催化，并创建新 `theme_cycle`；单纯价格反弹只进入待确认候选；
- `theme.record_status = archived/merged/invalid` 只能由人工或确定性实体合并规则触发；
- 人工覆盖有 `expires_at`，到期后恢复模型状态；
- 阈值采用滚动分位数并版本化，具体数值在种子数据回放后校准；
- 所有迁移与指标必须绑定 `cycle_id`，以便比较本轮与上一轮。

示例迁移规则：

```text
IF state = active
AND activity_delta_3d >= p80
AND breadth_delta_3d > 0
AND leadership_score >= 55
AND data_coverage >= 0.8
THEN propose state = accelerating
```

规则只生成 `proposed_transition`。状态提交器检查滞回、最短停留期和互斥条件后写入正式迁移。

## 6. 候选题材发现

候选发现采用多通道召回、受控归并：

```text
供应商新增题材/概念
官方/专业来源新实体词
多公司同类公告或互动主张
异常共振的公司簇
用户/研究员手工创建
  → 别名标准化
  → 与已有题材语义/成员/事件相似度检索
  → 新建 / 合并 / 作为子题材 / 进入人工审核
```

关键限制：价格共振只能召回候选，不能证明产业关系；Agent 可以建议别名和合并，不可自动执行。

## 7. 调度设计

### 7.1 MVP 日频

| 时间（Asia/Shanghai） | 任务 | 输出 | 目标完成时间 |
| --- | --- | --- | --- |
| 08:00 | 日历、来源健康、前日补数 | readiness | 08:10 |
| 09:00 | 盘前官方事件/公告增量 | event candidates | 09:15 |
| 15:10 | 收盘确认与行情完整性检查 | market watermark | 15:20 |
| 15:20 | 题材、成员、热榜、板块行情采集 | source snapshots | 15:40 |
| 15:40 | 标准化、实体解析、快照差分 | canonical facts/proposals | 16:00 |
| 16:00 | 指标、状态机、告警 | metrics/transitions/alerts | 16:20 |
| 16:20 | 日报和审核队列生成 | daily brief | 16:30 |
| 22:40 | 最晚热榜快照与日终封板 | sealed daily version | 23:00 |
| 02:00 | 校验、压缩、备份与可选补算 | quality report | 03:00 |

### 7.2 二期盘中

- 竞价关键快照：09:20、09:25、09:30；
- 盘中 1～5 分钟聚合，来源频率不足时按来源节奏；
- 10:30、11:30、14:00、15:00 形成固定观察截面；
- 高严重度事件可触发按需计算，但同一主题设置最短冷却时间；
- 盘中输出标记 `provisional`，收盘后用日终数据确认或撤销。

## 8. 幂等、版本与回放

### 8.1 幂等键

```text
source_snapshot: source + endpoint + business_date + cursor/window + content_hash
source_document: source + external_id + revision_id
metric: entity_id + metric_code + as_of + frequency + calc_version
transition: theme_id + from_state + to_state + effective_at + rule_version
alert: subscriber + change_event_id + rule_id + severity
```

重复采集不产生新事实；相同 external id 内容变化形成新 revision，不覆盖旧内容。

### 8.2 水位与封板

每个来源维护：

- `expected_until`：理论应有数据时间；
- `observed_until`：实际接收水位；
- `complete`：是否满足该批次完整性；
- `sealed_at`：版本封板时间；
- `reopened_reason`：封板后补数原因。

任何日报版本可被补数重算，但必须生成 `r2/r3`，不得静默替换 `r1`。

### 8.3 历史回放

回放输入只包括在目标 `as_of` / `business_date` 已可用的数据版本：

```text
published_at <= as_of
AND available_at <= as_of
AND available_trade_date <= business_date
AND valid_from <= as_of < valid_to
AND source snapshot sealed_at <= replay_cutoff
```

关系类回放必须声明查询模式：

- `strict_effective`：仅返回业务生效时间已知的关系；研究/回测默认使用；
- `observed_as_of`：允许纳入 `effective_from` 为空、但已观察的关系，并返回 `effective_time_quality=observed_only`。

成员评分与角色属于 derived 观察，不得回写 `theme_membership` 事实版本。生命周期状态与指标必须绑定 `theme_cycle.cycle_id`。

回放输出保存输入 manifest、代码/规则/指标版本和结果哈希。原始供应商未提供接入前历史时，明确返回 `history_incomplete=true`。

## 9. 告警逻辑

### 9.1 严重度

| 等级 | 典型事件 | 路由 |
| --- | --- | --- |
| 信息 | 一般成员变更、低级别新证据 | 日报 |
| 注意 | 生命周期变化、证据冲突、覆盖率显著下降 | 站内流 + 日报 |
| 重要 | 强度加速、关键官方催化、核心成员否认 | 站内即时 + 摘要 |
| 紧急 | 数据全面中断、错误历史污染、关键风险事件 | 运维与维护者即时 |

### 9.2 去重与抑制

- 同一 source document 的多条主张聚合为一个事件；
- 多来源转载通过规范 URL、标题相似、时间和正文指纹聚类；
- 同一题材同一变化类型在冷却期内更新原告警而非新增；
- 数据覆盖率不足时抑制业务告警，转发数据质量告警；
- 用户可设置每日即时告警上限，超出后进入摘要；
- 新证据明显提高严重度时允许突破冷却。

## 10. 失败与降级

| 故障 | 系统行为 | 禁止行为 |
| --- | --- | --- |
| 单来源失败 | 使用其它来源，标记 coverage 和 stale source | 把缺失当作成员退出 |
| 行情未封板 | 延迟强度计算，展示上次成功值和时间 | 用不完整截面生成正式状态 |
| 实体解析冲突 | 写入审核队列，保留原始标识 | 随机选择同名公司/题材 |
| Agent 不可用 | 规则摘要继续生成，提案等待 | 阻塞主数据和指标流水线 |
| 指标异常 | 隔离该版本，回退上次稳定版本 | 静默发布异常极值 |
| 通知失败 | outbox 重试、死信队列、幂等发送 | 重新计算业务事件制造重复告警 |

## 11. 运行可观测性

必须监控：

- 每来源成功率、延迟、行数偏差、schema 漂移、重复率；
- 实体解析成功/冲突/新实体比例；
- 成员日变化率和异常爆发；
- 指标覆盖率、分布漂移、极值比例；
- 状态迁移数量与每日基线偏差；
- 告警产生、抑制、发送和确认；
- Agent 工具调用成功、引用完整、成本和延迟；
- 日终版本是否按 SLA 封板。

数据质量门禁示例：

```text
IF source_row_count < rolling_median_20d * 0.6
OR unresolved_entity_rate > 0.05
OR member_change_rate > p99_120d
THEN quarantine batch
AND block lifecycle publication
AND open quality incident
```

## 12. 测试与验收

### 12.1 单元/契约测试

- 时间衰减、归一化、缺失覆盖和分数构成；
- 状态迁移、滞回、最短停留期和人工覆盖过期；
- `theme_cycle` 新建/结束与 record_status 隔离；
- 日快照差分、成员新增/退出候选；
- `strict_effective` / `observed_as_of` 与 `available_trade_date` 映射；
- 来源重复、修订、schema 漂移和幂等；
- 告警聚类、冷却、升级和每日预算。

### 12.2 回放测试

- 固定 20～30 个种子题材、至少 60 个交易日；
- 同一 manifest 重跑哈希一致；
- 修改未来证据不影响过去状态；
- 补数只产生新 revision，不覆盖已封板输出；
- 断掉任一来源后系统降级且不制造批量退出。

### 12.3 质量验收

- 90% 以上日终版本在 23:00 前封板，目标正式上线后提高到 99%；
- 高等级告警均可解释到触发规则和输入；
- 供应商中断不会造成错误成员退出；
- 任意题材任意日可导出版本 manifest；
- Agent 完全关闭时核心监测仍可运行。
