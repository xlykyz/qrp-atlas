# 动态产业-题材库：数据基座需求

> 本文是需求与契约设计，不是建表迁移。实现时仍遵循 QRP `pipeline → contracts → DuckDB → indicators → API` 边界。

## 1. 设计目标

- 同时表达稳定行业、产业链关系和动态题材，且三者分模维护；
- 保存来源原貌、QRP 标准实体和派生指标之间的完整血缘；
- 支持 point-in-time 查询、双时态修订和历史回放；
- 支持多来源冲突、未知、不确定和人工审核；
- 为 Web、告警、研究回测和 AI Agent 提供同一数据契约；
- 明确全局 canonical、可重算 derived 与用户私有对象边界；
- 首期适配 DuckDB，不依赖图数据库或消息队列才能运行。

## 2. 数据分层

```text
L0 Source Snapshot
  原始响应、请求参数、来源时间、内容哈希、授权元数据

L1 Canonical Fact
  标准实体、事件、来源文档、供应商成员快照、行情事实

L2 Curated Knowledge
  QRP 题材版本、产业关系、题材成员事实、证据与已批准审核决策

L3 Derived Signal
  指标、成员评分、角色观察、生命周期状态、变化事件、告警、摘要

L4 Serving View
  今日总览、题材详情、成员视图、时间轴、Agent 工具结果

Owner-Private Workspace
  研究笔记、个人订阅、个人告警偏好、未提交提案、个人审核草稿、Agent run
```

L0/L1 只能通过 pipeline 和 contracts 写入；L2 的人工/Agent 操作先生成 proposal，经审核器提交；L3 可由固定输入重算；L4 不保存新的业务真相。`theme.current_version_id` 与任何“当前状态指针”只可作为 L4 缓存，不得成为 PIT 权威来源。

## 3. 实体关系

产业库、题材库和市场身份必须分模，不得把公司—产业环节关系绑死在某个题材成员上：

```text
ASSET  ↔  CHAIN_NODE     业务事实：产品、产能、客户、供应关系
THEME  ↔  CHAIN_NODE     某轮题材影响哪些产业环节
THEME  ↔  ASSET          市场题材成员与市场身份
THEME  ↔  THEME_CYCLE    题材市场周期（本轮/上轮比较）
```

### 3.1 三类对象边界

| 分区 | 对象 | 写入路径 | 可见性 |
| --- | --- | --- | --- |
| 全局 canonical | `theme`、taxonomy/chain、已批准证据、标准产业关系、标准题材成员事实 | pipeline / 审核提交器 | 全产品只读共享 |
| 可重算 derived | 题材指标、成员相关度/角色观察、生命周期状态、变化事件、告警摘要 | indicators / 状态机 | 全产品只读共享 |
| 用户私有 | `research_note`、subscription、个人 alert 偏好、未提交 proposal、个人审核草稿、`agent_run` | 用户或 Agent 工作区 | 仅 `owner_id` 可见 |
| 受控共享 | 已提交 proposal、review task、canonical commit 审计 | 提交后进入审核队列 | 按角色可见 |

私有对象必须包含 `owner_id`。审核队列不得仅靠 `requester_id` 间接隔离；需定义 Viewer / Researcher / Reviewer / Maintainer / Admin 的可见范围。

### 4.3 分类、题材与别名

#### `taxonomy_node` / `chain_node`

```text
node_id, taxonomy_type, classification_system,
node_code, node_name, parent_node_id, level,
valid_from, valid_to, source_id, version
```

`taxonomy_type`：`industry`、`chain_stage`、`product`、`technology`、`application`、`policy_domain`。产业链节点与行业分类共用 taxonomy 基础设施，但业务写入路径独立。

#### `chain_edge`

```text
edge_id, from_node_id, to_node_id, relation_type,
direction, strength, evidence_status,
published_at, available_at, available_trade_date,
observed_at, ingested_at,
effective_from, effective_to,
valid_from, valid_to, source_id, version
```

`relation_type` 示例：`upstream_of`、`supplies`、`substitutes`、`enables`。产业边不依赖题材存在。

#### `asset_chain_relation`

```text
relation_id, asset_id, chain_node_id,
relation_kind, product_or_capacity_note,
structural_role, relation_status,
published_at, available_at, available_trade_date,
observed_at, ingested_at,
first_observed_at, last_observed_at,
effective_from, effective_to,
valid_from, valid_to,
origin_type, origin_id, version,
review_status, reviewed_by, reviewed_at
```

`relation_kind` 示例：`produces`、`supplies`、`consumes`、`customers_in`、`capacity_in`。
这是公司—产业环节的长期业务事实，可跨多个题材复用，不得嵌入 `theme_membership`。

#### `theme_chain_link`

```text
link_id, theme_id, chain_node_id, cycle_id,
impact_direction, impact_scope, link_status,
published_at, available_at, available_trade_date,
observed_at, ingested_at,
effective_from, effective_to,
valid_from, valid_to,
origin_type, origin_id, version,
review_status
```

表达“某轮题材影响哪些产业环节”，与公司产业关系解耦。

#### `theme`

```text
theme_id, canonical_name, theme_type,
record_status, merged_into_theme_id,
created_at, created_by
```

- `theme_type` 示例：政策、技术、产品、涨价、供需、事件、地域、改革；类型是研究维度，不等于供应商分类。
- `record_status`：`active`、`archived`、`merged`、`invalid`。归档、合并、错误实体属于实体治理状态，不是市场生命周期。
- 不在 canonical 表中保存权威 `current_version_id` / `current_cycle_id`；这些指针只存在于 serving view 缓存。

#### `theme_version`

```text
theme_version_id, theme_id, version_no,
name, short_definition, inclusion_rule, exclusion_rule,
parent_theme_id, valid_from, valid_to,
effective_from, effective_to,
change_reason, proposal_id, created_by, created_at
```

`valid_*` 表示 QRP 何时认可该版本，`effective_*` 表示版本描述的业务有效区间；两者不可混用。

#### `theme_cycle`

```text
cycle_id, theme_id, cycle_no,
started_at, ended_at,
root_catalyst_ids, previous_cycle_id,
start_reason, end_reason,
created_at, created_by
```

- 一次“复燃”创建新的 `theme_cycle`，而不是把 `reactivated` 塞进生命周期状态机；
- 本轮与上一轮题材行情比较必须基于 `cycle_id`；
- 周期内状态迁移写入 `theme_lifecycle_transition`，只允许：
  `candidate → emerging → active → accelerating → diverging → cooling → dormant`。

#### `theme_alias`

```text
alias_id, theme_id, alias, alias_type, source_id,
effective_from, effective_to, valid_from, valid_to,
match_confidence, review_status
```

别名可包括供应商名、市场简称、旧称和英文名。同一 alias 映射多个 theme 时必须进入冲突审核。

#### `source_theme_snapshot`

```text
source_id, source_theme_code, source_theme_name,
trade_date, metric_payload_json, snapshot_id,
first_observed_at, last_observed_at
```

该表保留供应商口径，绝不直接替代 `theme`。

### 4.4 公司-题材事实、派生评分与证据

## 5. 时间契约

### 5.1 必备时间字段

MVP 是日频产品，因此时间契约必须同时保留墙钟时间与交易日映射，不能只留 `available_at`。

| 字段 | 含义 |
| --- | --- |
| `event_time` | 现实世界事件发生时间 |
| `published_at` | 来源首次公开时间 |
| `available_at` | QRP 在规则上允许使用该信息的最早墙钟时间 |
| `available_trade_date` | 将该信息映射到可进入计算的交易日（复用 QRP 现有 PIT 语义） |
| `observed_at` | 采集器实际观察到的时间 |
| `ingested_at` | 写入系统的时间 |
| `effective_from/to` | 事实描述的业务有效区间；未知时允许为空 |
| `valid_from/to` | 该版本在 QRP 中被认可的系统区间 |
| `trade_date` | 供应商或市场快照所属交易日 |
| `as_of` | 查询/计算的知识截止点（墙钟或带时区时间戳） |
| `business_date` | 查询/计算目标业务日（交易日） |

规则：

- 盘后发布的信息是否可进入“当天”指标，统一由 `available_trade_date` 决定，而不是前端自行按 `available_at` 猜测；
- 公告在收盘后发布时，`available_trade_date` 通常映射到下一交易日；
- 任何指标、成员评分、生命周期计算的 `input_manifest` 必须记录所用 `as_of` 与 `available_trade_date` 规则版本。

### 5.2 两种 PIT 查询模式

#### A. `strict_effective`

仅返回真实业务生效时间已知的关系：

```sql
WHERE theme_id = :theme_id
  AND valid_from <= :as_of
  AND (valid_to IS NULL OR :as_of < valid_to)
  AND available_at <= :as_of
  AND available_trade_date <= :business_date
  AND effective_from IS NOT NULL
  AND effective_from <= :business_date
  AND (effective_to IS NULL OR :business_date < effective_to)
```

#### B. `observed_as_of`

允许纳入首次观察关系，但必须标记时间质量：

```sql
WHERE theme_id = :theme_id
  AND valid_from <= :as_of
  AND (valid_to IS NULL OR :as_of < valid_to)
  AND available_at <= :as_of
  AND available_trade_date <= :business_date
  AND (
        (effective_from IS NOT NULL
         AND effective_from <= :business_date
         AND (effective_to IS NULL OR :business_date < effective_to))
     OR (effective_from IS NULL
         AND first_observed_at IS NOT NULL
         AND first_observed_at <= :as_of)
  )
```

返回字段：

- `effective_time_quality = known | observed_only`
- `effective_from` 为空时不得伪装成已知生效日；
- 产品展示“最早观察于”，研究/回测默认使用 `strict_effective`，发现/审核可用 `observed_as_of`。

供应商只给日快照而不给真实纳入日期时：

- `first_observed_at` 记录首次看到；
- `effective_from` 可为空；
- 禁止把 `first_observed_at` 直接改名为业务生效时间；
- 禁止因为 `effective_from` 为空就把 observed-only 关系在 strict 模式下偷偷放行。

### 5.3 未来函数与回填禁令（最低测试）

至少覆盖三类测试：

1. **收盘后公告不得进入当日收盘计算**  
   `published_at` 在收盘后、`available_trade_date = 下一交易日` 的证据，不得进入当日 `theme_metric_observation` / 成员评分。
2. **后续修订不得回写早期 as-of**  
   T+n 修订生成新 `valid_from` 版本；以 T 日 `as_of` 查询不得看到修订后内容。
3. **当前供应商成员不得回填到首次接入日前**  
   接入日前没有快照时，不得用“当前成员”回填历史；应返回 `history_incomplete=true`。

## 6. 标识、版本与血缘

### 6.1 稳定标识

- `theme_id` 使用 QRP 内部稳定 ID，不使用供应商代码作主键；
- 供应商代码保存在 source mapping，可多对一/一对多；
- 公司沿用现有 `asset_id/ticker` 标准；
- 文档使用 source + external_id + revision，URL 不是唯一键；
- 事件使用规范指纹辅助聚类，但人工可拆分错误聚类。

### 6.2 输入清单

每次指标/状态计算保存 `input_manifest`：


## 7. 数据来源优先级

### 7.1 MVP 必需

| 类别 | 首选 | 备选/补充 | 验收 |
| --- | --- | --- | --- |
| 行业历史 | 现有申万历史 | 中信行业 | as-of 唯一归属 |
| 题材目录/成员 | Tushare DC/KP 授权接口 | THS/TDX、人工种子 | 至少 60 日可回放或明确历史起点 |
| 板块/个股行情 | QRP 现有日线 + DC 板块行情 | 本地合成等权组合 | 日终完整性与口径保存 |
| 涨跌停/热榜 | QRP 现有涨停池 + Tushare 热榜/强势板块 | 其它授权源 | 日内快照时间可辨 |
| 官方证据 | 公告、交易所互动、政府/监管 | 公司官网 | published/available 可确认 |
| 专业解释 | 授权研报/新闻摘要 | 人工笔记 | 版权边界明确 |

### 7.2 二期增强

- 竞价与分钟行情；
- 商品现货/期货价格和产业高频数据；
- 搜索趋势、社媒和新闻注意力；
- 招投标、专利、产能、价格和供应链事件；
- 多供应商概念成员交叉验证。

## 8. 数据质量规则

### 8.1 完整性

- 每批来源行数与 20 日滚动中位数比较；
- 关键字段非空率、唯一键、交易日覆盖；
- 题材成员数异常突变隔离；
- 指标输出必须附 coverage。

### 8.2 一致性

- 同一供应商题材代码同一交易日唯一名称；
- 同一来源文档同一 revision 内容哈希固定；
- 同一主题同一时点仅一个有效正式版本；
- lifecycle transition 的 `from_state` 必须等于当前状态；
- 审核决策必须能定位 resulting version。

### 8.3 合理性

- 收益、换手、热度和资金字段做单位与极值检查；
- 题材规模过小/过大单独标识；
- 成员批量退出不在来源缺失时提交；
- 新别名与已有 canonical name 冲突时阻断自动合并；
- AI 抽取数值必须与引用片段做字符串/单位校验。

## 9. 服务视图

为 API 预计算以下读模型，避免前端拼装事实：

- `theme_overview_asof`：题材定义、当前周期、状态、分数、覆盖、主催化；`current_version_id/current_cycle_id` 仅作缓存指针；
- `theme_member_lens_asof`：成员事实 + 派生双轴分数 + 角色观察 + 证据状态；
- `theme_chain_lens_asof`：题材影响的产业环节、公司产业关系联查结果；
- `theme_event_timeline`：事件、变化和生命周期合并时间轴，可按 `cycle_id` 过滤；
- `theme_daily_change_summary`：当日新增/增强/分歧/退潮；
- `theme_version_diff`：两个版本的定义、别名、成员和状态差异；
- `theme_cycle_compare`：本轮与上一轮周期指标/成员/催化比较；
- `monitor_alert_feed`：已聚类告警及解释（按 owner 过滤）；
- `review_queue`：按角色可见的提案、证据、冲突和相似历史决策。

所有 serving view 接受 `as_of`，默认值由服务端返回并显示，前端不得隐式使用本机当前时间推断。

## 10. 存储与性能建议

MVP 保持 DuckDB：

- 日频来源和事实使用按 `source/business_date` 的分区文件或现有入库方式；
- JSON 只存供应商扩展字段和解释组件，核心筛选字段列式化；
- 日快照成员可存全量，另生成差分表用于查询；
- 高频明细若进入二期，先按日 Parquet，再在 DuckDB 聚合；
- 图关系在关系表中表达，只有多跳查询成为真实瓶颈时才评估图数据库；
- Agent 读取专用 API/工具返回限量结构化结果，不开放任意 SQL。

建议性能目标：

| 查询 | P95 目标 |
| --- | --- |
| 今日题材列表（500 内） | < 500 ms |
| 单题材概览 | < 700 ms |
| 单题材成员（300 内） | < 800 ms |
| 60 日指标曲线 | < 500 ms |
| 两版本差异 | < 1 s |
| Agent 单次结构化工具 | < 2 s（不含模型） |

## 11. 数据验收门禁

实现进入前端联调前必须满足：

- 20～30 个种子题材 canonical ID 稳定；
- 每个题材至少一个定义版本、一个来源映射、一个 `theme_cycle` 和一个 `theme_chain_link`；
- 独立维护 `asset_chain_relation` 金标准，不得只存在于题材成员表；
- 200～300 条人工金标准题材成员关系，含支持、反对和未知样本；
- `theme_membership` 不含相关度分数和 core/follower 身份字段；
- 任意历史日 as-of 查询不返回未来证据，且 `available_trade_date` 映射正确；
- `strict_effective` / `observed_as_of` 两种模式行为可测；
- 收盘后公告、后续修订、接入前回填三类未来函数测试为 0 泄漏；
- 来源失败重跑幂等，修订形成新版本；
- 日快照批量缺失不产生成员退出；
- 指标、状态、告警均能回到 input manifest；
- 私有对象带 `owner_id`，审核队列按角色隔离；
- Agent 无数据库凭证，工具无法越权写标准事实。
