## 3. 根因链（已确认）

```
① 调度冲突：market-daily-close 与 adj-factor-close 同被调度在 16:15
        ↓
② 竞态：adj 抢跑（早于 market 启动 8~41 秒）
        ↓  错误码 MARKET_DAILY_INPUT_STALE（当日 market 产出尚不存在）
③ adj-factor-close FAILED（08-11/17/18/20/24/28 共 6 个交易日）
        ↓
④ system-b-readiness-daily BLOCKED（"dependency adj-factor-close latest status is FAILED"）
        ↓
⑤ system-b-state-daily BLOCKED → 当日 state 观测整日缺失（无回填机制）
        ↓  （08-04 为另一成因的单日遗漏，见 §2）
⑥ episode 全量重建跨过缺口 → 相邻行差分产生 958 次假 BASE->ACTIVE（2026-08）
        ↓
⑦ segment 不变量 active_sprint_count_mismatch 判定 929 违规
        ↓
⑧ 同一事务内校验失败 → 整体回滚（segment 表未落盘、池链阻塞）
```

| 08-31 起（现行） | 08:25 UTC（16:25 CST） | 08:15 UTC（16:15 CST） ← 已错开 |

异常日逐次时间线（UTC）：

| 日期 | adj 启动 | market 启动 | 结果 |
| --- | --- | --- | --- |
| 08-11 | 08:15:02 | 08:15:39 | adj 早 37 秒 → FAILED |
| 08-17 | 08:15:02 | 08:15:10 | 早 8 秒 → FAILED |

**机制**：同批次到期的两个 job 之间无"先 market 后 adj"的顺序保证；当 adj 抢先启动时，其 Contract 的 freshness 检查（要求当日 `daily_market_snapshot` 已产出）必然失败。scheduler 的依赖检查未拦截——依赖满足性判定与 Contract 的 freshness 判定存在口径缺口（前者基于历史运行状态，后者基于当日真实产出）。

### 3.2 环节④⑤：阻塞级联与缺口形成（证据）

- readiness 的 5 次 BLOCKED，`error_summary` 字面一致：`dependency adj-factor-close latest status is FAILED`；
- 对应 5 个日期的 state 观测行数均为 **0**（整日缺失），且事后**无回填**；
- `FAILED` 是终态、系统无自动重试；`BLOCKED` 会被持续重新评估（依赖恢复即解锁补跑）——08-28 的补齐正依赖于此（人工 RETRY 上游后，被阻塞的整条链自动补跑）。

### 3.3 环节⑥：958 次假 `BASE->ACTIVE`（证据）

2026-08 的 `BASE->ACTIVE` 与"缺口日后的首个有数据日"严格对应，总量精确吻合：

| --- | --- | ---: |

**机制**：episode 重建读取 state 观测表；缺口使相邻两行跨过缺失交易日，`trend_state` 差分被误判为 `BASE->ACTIVE`（真实路径为停牌/缺失前后的 `CANDIDATE->ACTIVE` 等）。该假迁移不被计入 `ma5_reentry_count`，而 segment 按 `trend_state` 连续区间照常开新 ACTIVE 段 → 两侧计数分叉。

- 事务结构（`BEGIN → ensure_schema → DELETE/INSERT → audit → COMMIT/ROLLBACK`）在旧代码即存在；segment 的 11 个新 invariant 被并入同一 `violations` 判定 → 校验失败即整体回滚。

## 4. 关键机制与缺陷定性（已确认）

### 4.1 下游派生阻断上游业务（连坐回滚）

`episode` 重建与 `segment` 派生位于**同一事务**、共用**同一 fail-closed 判定**：

```python
violations = {k: v for k, v in audit["quality"].items() if v and k != "shared_boundary_days"}
if violations:
    raise ...("INVARIANT_VIOLATION", ...)   # → 整个事务回滚（含 episode/observation）
```

- 旧代码（`167b1af`）：`quality` 仅含 26 个 episode/observation 自身不变量；
- 新代码（`d991880`）：新增 11 个 segment 不变量（含 `active_sprint_count_mismatch`），**判定逻辑一字未改**；
- 结果：segment（自称"纯下游确定性派生"）获得了对上游业务提交的**否决权**。本次回滚掉的 episode/observation 重建结果与缺口无关，属连坐损失。

### 4.2 为何"新代码首次运行"才暴露

- segment 逻辑 09-02 即合入仓库，但生产服务自 08-30 22:53 起未重启，一直运行 08-07 时代的代码（经 `merge-base --is-ancestor` 验证不含 segment）；
- 09-10 05:22 的重启首次加载含 segment 的代码 → 当日 18:50 首次真实运行 → 暴露。

### 4.3 状态机的判断语义与“非法迁移”的两种类型

**判断语义**（`src/qrp_atlas/indicators/system_b/state_machine_v2.py`）：状态机**不比较价格**，只消费上游预置的布尔事实
（`latest_actual_is_above_or_equal_ma5`，记 `L`；`previous_actual_is_above_or_equal_ma5`，记 `P`）：

```python
base      = L == False                     # 当日收盘在 MA5 下方
candidate = L == True  and P == False      # 在上方、前日下方（上穿）
active    = L == True  and P == True       # 在上方、前日也在上方（持续）
```

由此得出一条硬性不变量：`P(t)` 与 `L(t-1)` 是**同一个事实**（“前一日收盘是否 ≥ 其 MA5”），必须恒等。
因此 `BASE->ACTIVE` 在语义上**不可达**：

```
状态 t-1 = BASE ⟹ L(t-1) = False ⟹ P(t) = False ⟹ 状态 t 只能为 CANDIDATE
```

**推论**：任何 `BASE->ACTIVE` 都对应两种原因之一——
① `P(t) ≠ L(t-1)`（上游事实自相矛盾）；② 相邻两行之间存在**未被写入/被过滤掉的观测行**。
据此，967 次假迁移分为两类：

| 类型 | 次数 | 机制 | 状态 |
| --- | ---: | --- | --- |
| 一：缺口型 | 958 | state 行整日缺失；状态机内部判断本正确（该行记录的 `previous_trend_state=CANDIDATE`、`previous_actual_trade_date` 指向缺失日），是 episode 对表内相邻行做简单差分导致的误读 | 已确认（§3.3） |
| 二：口径接缝型 | 1（全表共 6 处 `P≠L` 矛盾） | 相邻两行由**不同代码状态**的运行产出，同一事实被两个价格口径算出相反结论 | **已定性**（§4.4） |

**实例对照**（同一现象、两种成因）：

- 类型一（`300926.SZ` 2026-08-12）：state 表缺 08-11 行；08-12 行自身记录 `prev_actual=08-11`、`prev_trend=CANDIDATE`——内部判据合法，仅行缺失。
- 类型二（`600004.SH` 2026-07-27）：两行都在且相邻，但 07-24 行的 `L=False` 与 07-27 行的 `P=True` 直接冲突。

### 4.4 类型二定性：口径接缝（第二个独立缺陷）

**定义**：同一票的相邻两行由**不同 HEAD 代码状态**的两次运行分别产出，且两侧使用的价格口径不同；
两段数据互不回溯重写，在表中形成永久“接缝”。

**全表扫描结果**（17,957,741 个可比行）：`P(t) ≠ L(t-1)` 的矛盾仅 **6 处**，全部落在**两处接缝**上：

| 接缝 | 冲突行 | 两侧来源运行 | 口径差异 |
| --- | --- | --- | --- |
| **2013-01-04** | `000796.SZ`、`002662.SZ`（方向 ACTIVE→BASE） | 2012-12-31 及以前 ← 运行 `3ca0a068`（08-03 16:20）；2013-01-04 起 ← 运行 `ceaf8d2b`（07-27 03:37） | 两条 INITIALIZE 段（`None~2013-01-03` 与 `2013-01-01~2026-07-24`）拼接 |
| **2026-07-27** | `600039.SH`、`002713.SZ`（未跳变）、`603158.SH`、`600004.SH`（跳变为 ACTIVE） | 07-24 及以前 ← `ceaf8d2b`（07-27 03:37）；07-27 起 ← `4632ef3e`（08-03 16:30） | 前复权逻辑（提交 `fad4fa6`，07-26 引入）在两次运行间生效 |

**根因定性（已认可）**：

> **算法换了，但已写入的旧数据没有重算。**

- 引入前复权（`close = raw_close × adj_factor / latest_adj_factor`）本身是正确改动——它消除除权日附近 MA5 的口径混用；
- 但 07-27 03:37 的 INITIALIZE 是在 **docs 分支**（不含该逻辑，经 `git branch --contains fad4fa6` 验证）上运行的，产出原始价口径；
- 08-03 16:30 起的补跑在含该逻辑的分支上运行，产出前复权口径；
- **旧段未被重算**，接缝处同一事实（07-24 收盘 vs 其 MA5）在两段中结论相反：
  - 旧口径：`7.67 < 7.882`（原始价 MA5，窗口混用除权前后价格）→ `L=False`；
  - 新口径：`7.67 > 7.658`（前复权 MA5）→ `P=True`。

**为何“除权普遍但只有 6 次冲突”**（三重条件同时满足才会暴露）：

1. 冲突只在“**不同口径的运行先后写入同一张表**”的接缝处产生——日常除权不产生冲突（同一批运行内相邻行自洽）；全库此类接缝仅两处；
2. 接缝两侧必须恰好是**同一票的邻接行**——2026-07-24 当天除权的票有 20 只，均为潜在冲突点；
3. 还需**关系恰好翻转**（除权日收盘价落在“旧口径 MA5”与“新口径 MA5”之间）——20 只中仅 2 只（`603158.SH`、`600004.SH`）翻转成 `ACTIVE`。

**附带观察（待核）**：`002713.SZ` 的除权日不在 07-24，却也在该接缝出现 `P≠L` 矛盾——
说明接缝影响不限于除权票（两侧的 `latest_adj_factor` 基准可能因运行覆盖范围不同而不同），需后续逐票核验。

**证据一：状态中断的年份分布**（“中途 NULL 行”= 该行趋势为空且此前曾有过非空状态）：

| 2015 | 244 | 3 |
| 其余全部年份（1990–2026） | **0** | 0 |

其它年份的“ACTIVE 且前行 NULL”均为**新股首态**（其“更早的非空状态”为“无任何历史状态”），不构成跨间隙迁移。

**证据二：缺失层的定位**（`src/qrp_atlas/pipeline/system_b/repository.py:248-268`）：
`UNRESOLVED_MISSING` 判定条件 = 交易日历有该日 **∧** 无停牌记录 **∧** 行情快照（`daily_market_snapshot`）无该行。

**证据三：数据源验证（2026-09-11，只读）**：
通过项目统一网关（`get_tushare_pro()`，第三方 Tushare-compatible 代理）拉取 2013-12 全月日线，与数据库逐日比对：

| 对比 | 结果 |
| --- | --- |

**证据四：缺失规模**：2013 年 255 只票 × 102 个交易日（3,044 个“票-日”组合，其中 12 月占 2,722）；2014 年 4 只票（235 个组合）。

**性质**：历史数据固有空洞（约 13 年前，源侧已无）。与类型一（运行故障）不同：**不可修复**，只能隔离或让其下游具备容忍能力。

## 7. 候选修复方向（**未定案**；本节不预设最终方案）

> **本报告不预设最终解决措施。** 本节仅为候选方向清单，供审计与后续决策参考；
> 采用哪些、以何顺序与形式实施，由独立决策流程另行确定。所有候选**均未实施**。

| 层次 | 问题 | 候选方向 | 备注 |
| --- | --- | --- | --- |
| ① 最源头 | 同批次依赖无顺序保证；“依赖满足”存在两套口径 | 修复 scheduler 的同批次依赖语义（下游必须等上游**本次**完成） | 现行仅靠 schedule 错开 10 分钟规避；若 market 某天超时仍会重现 |
| ② 数据一致性（口径接缝） | 跨口径运行在同一张表拼接、旧段未重算（§4.4） | ① 每次运行后做接缝一致性校验（断言 `P(t) == L(t-1)`，不成立即触发该区间重算）；② 保证同一票邻接区间由同一口径生成（或全量重算） | 消除 §4.4 的 6 处矛盾；`002713.SZ` 类非除权接缝需先核验 |
| ③ 状态机加固 | 矛盾输入会静默产出“语义上不可能”的状态 | 在状态机入口增加断言 `P(t) == L(t-1)`（当 `prev_actual(t) == latest_actual(t-1)`），使矛盾输入显式失败 | 把“任何时候不应出现 BASE->ACTIVE”变成可执行约束 |
| ④ 数据欠账 | 6 天 state 缺口无回填机制 | 设计回填路径（注意：retry 复用原 `scheduled_at`，历史日期补跑需验证 target-date 解析） | 消除 958 次中的绝大部分 |
| ⑤ episode 差分语义 | episode 对表内相邻行做简单差分，跳号时产出假迁移 | 改为消费行内自带的 `previous_trend_state`/`state_transition` 事实，或将“跳号行”判为不可比 | 可同时覆盖类型一（958）与类型三（8）；**不应**通过放宽 segment invariant 来容忍 |
| ⑥ 隔离设计 | 下游派生失败连坐上游提交 | 校验分离（segment violations 独立判定）或分事务 | 与成因认定相互独立，可先行 |
| ⑦ 运维机制 | FAILED 为终态、无自动重试；缺口不告警 | 缺口检测与告警、（可控的）自动补偿 | — |
| ⑧ 历史数据空洞（2013/2014） | 源侧无数据、不可修复（§4.5） | 候选：将 segment 的计算与检测起点限定在 2015 以后；或由 ⑤ 的差分语义修复一并覆盖 | 属产品范围内取舍，需决策；若限定范围，须先明确影响面（仅限 segment 派生 vs 改 episode 重建起点 `ACCEPTANCE_START_DATE`） |

> 说明：原“修正 invariant 口径”的提法已按 §4.3/§4.4 的语义分析修订——**不应放宽 segment 的 invariant 去容忍 `BASE->ACTIVE`**（那是掩盖症状）；正确路径是让上游事实一致（②③）并让下游正确消费迁移事实（⑤）。invariant 在上述修复到位后应自然恒真。
