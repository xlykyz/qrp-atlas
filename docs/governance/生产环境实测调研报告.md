### 缺口 7 ｜ 迁移编号排序是否被迁移执行器依赖

**实测结论**

- **不存在按编号排序执行的迁移执行器**：
  - 全仓库搜索 `deploy/duckdb` 引用，**唯一命中为测试** `tests/contracts/test_schema_contracts.py`（读取 `003`/`007`/`010` 做 DDL 与 `contracts/schema.py` 的字段一致性校验，**不执行迁移**）；
  - `004_migrate_ingested_at_to_timestamptz.sql` 文件头自述：*"This migration is EXPLICIT and NON-AUTOMATIC."*；
  - 生产库无迁移记录表（见缺口 5），无自动迁移追踪。
- 实迁路径为**人工显式执行**（walkthrough 中的形态为 `duckdb <db> < deploy/duckdb/NNN_*.sql`）。
- **编号现状**：`002`×1、`003`×2（`003_stock_collections_and_m4.sql` 与 `003_system_b_pools.sql`）、`004`–`010` 各 1；该目录缺 `001`（`001_auth_schema.sql` 在 `deploy/postgres/`）。

**→ 结论：编号排序不被任何执行器依赖**，`003` 重号**不构成运行时风险**；其真实代价是人工执行与审计时的歧义。台账 C-05 可据此重估严重度。

## 4. 生产实况快照（超出 §8 的实测发现）

1. **安全面**：`QRP_API_CORS_ORIGINS = *` 且 API 监听 `0.0.0.0:8000`，认证为 `local` 模式（会话 TTL 7 天）。生产经 Caddy 反代对外，建议治理流程评估 CORS 与暴露面的收窄。
2. **空表率**：主库 58 张表中 **30 张为空**，集中在尚未投产的域（`theme*` 全体 8 张、人气双表、System B 决策链 4 张、`trade_execution`、排名快照 4 张、`market_phase`、`stock_collection` 等）。"schema 先行、能力未挂载"是当前主库的基本形态。
3. **数据双份**：主库 `irm_interaction_qa`（6,283 行，止于 2026-08-02）与 IRM 独立库（19,451 行，活跃）并存，见缺口 5 说明。
4. **依赖级联是主要失败放大机制**：494 次 FAILED 中大量被 BLOCKED 依赖链放大（如 `etf-daily-close` 单点失败引发 `etf-adj-factor-close` 26 次 BLOCKED；`system-b-episode-daily` 单次失败引发 3 条 pool 任务阻塞）。
5. **治理进展的量化证据**：IRM（423 次历史失败）与 ETF（26 次历史失败）两条最严重的失败线，在 09-09 服务重启加载当前基线代码后**均已恢复**，可作为"运行时热修需配套重启"的实证案例。
