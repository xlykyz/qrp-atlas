## Frontend Development Guidelines

本文件适用于 `web/` 及其全部子目录。目标是让 qrp-atlas 的前端长期可维护、可扩展、可重构，并始终通过稳定 API 使用后端能力。

页面负责组装，组件负责展示，hooks 负责状态和副作用，api 层负责请求，lib 负责纯函数，types 负责类型。新增功能不能继续堆进页面文件，也不能把后端量化逻辑复制到浏览器。

### 1. 核心原则

- 前端只通过 API 使用数据、策略、任务和结果；不得直接访问 DuckDB、结果目录或 Python 对象。
- 新增或重构功能时优先保持现有业务行为不变。
- 除非任务明确要求，不顺手修改 UI 风格、不改变 API 协议、不引入新的状态管理库、不重写无关模块。
- mock 只用于离线开发和演示，不得成为真实产品模式的隐式回退。
- 认证、owner 隔离、PIT、成交和绩效计算由后端强制执行；前端隐藏或校验不能替代后端权限与契约。

### 2. 推荐结构

```text
web/src/
  pages/                         # 路由页面，只做组装
  features/<feature>/            # 业务功能模块
    components/
    hooks/
    lib/
    types.ts
  shared/
    components/
    hooks/
    lib/
  api/                           # facade、adapter 与请求封装
    adapters/
    mock/
  types/                         # 跨模块共享类型
```

当前主要 feature 包括：

```text
overview
stock-review
raw-preview
review-logs
backtest
backtest-workflow
```

新增独立业务能力时优先建立新的 `features/<feature>/`，不要继续扩大无关 feature 或页面文件。

### 3. 页面文件约束

页面文件应保持轻量，主要负责：

- 读取路由参数；
- 调用 feature hooks；
- 组合 feature components；
- 管理页面级布局和少量导航状态。

页面文件不应长期承载：

- 复杂数据请求；
- 大量 `useEffect`；
- 图表生命周期；
- 表单提交和 DTO 转换细节；
- 表格排序、筛选、分页细节；
- 大量业务计算；
- 重复工具函数；
- 策略、成交、绩效或权限算法。

如果页面接近或超过约 300 行，新增功能前应优先评估拆分。行数只是信号，不应为了满足数字机械拆出无意义文件。

### 4. Feature 与复用规则

- 跨页面复用的能力放入 `shared/`。
- 某个业务功能专属的能力放入 `features/<feature>/`。
- 所有后端请求必须经过 `api/` 层，不要在页面或组件里直接写裸 `fetch`。
- 已有公共工具函数时必须复用，不要重复定义百分比、金额、成交量、日期、颜色 class 等格式化能力。
- feature 之间不要互相导入内部组件或 hook；需要共享时提升到 `shared/` 或稳定公共 API。
- 不因单个页面需要就在全局 `types/` 中堆积局部类型。

### 5. API 与 adapter 规则

前端数据访问分层：

```text
pages / features
→ api facade
→ adapter interface
→ http | mock implementation
```

必须遵守：

- 页面、组件和 feature 不得直接 import `api/mock/*`；
- HTTP 与 mock adapter 实现同一前端协议；
- 默认真实模式由环境配置决定，不允许请求失败后悄悄切换 mock；
- API DTO、表单模型和展示模型应显式转换，避免一个类型承担所有边界；
- 后端字段新增或语义变化时先更新 adapter/types，再更新页面；
- 错误响应必须转换为稳定、可展示的前端错误，不吞掉真实失败；
- 不在前端维护与后端 catalog、策略版本、任务状态机或结果公式平行的事实来源。

### 6. 策略与回测工作流边界

`backtest-workflow` 负责配置和编排，不负责运行策略。

允许：

- 显示后端策略目录和版本；
- 根据 schema 构建参数表单；
- 组装股票池、日期、成本和执行配置；
- 创建任务、轮询或读取任务状态；
- 打开真实 run、历史、比较和重放结果；
- 在 mock 模式下使用集中 fixture 演示界面。

禁止：

- 在浏览器中复制 Python 指标或策略算法；
- 自行判断真实成交、T+1、涨跌停或停牌结果；
- 在页面中硬编码正式策略清单、稳定版本或参数默认值；
- 通过前端传入任意 owner 获取其他用户任务或结果；
- 将 mock run 标记或展示为真实持久化运行。

### 7. 图表与大表格规则

- 图表逻辑必须和页面逻辑分离：组件负责渲染，hook 负责生命周期，lib 负责数据转换。
- 图表库实例必须正确创建、更新和销毁，避免重复绑定和内存泄漏。
- 大表格必须考虑滚动边界、冻结表头/列、分页或虚拟滚动。
- 横向滚动应限制在表格容器内部，不能导致整个页面横向滚动。
- 结果图表不得在前端重新计算与后端标准结果冲突的绩效口径；只做必要的展示转换。

### 8. 表单、状态与 URL

当前阶段默认不引入 Redux、Zustand、MobX 等全局状态库。

优先使用：

- 组件内部 state；
- 页面级或 feature 级 hook；
- URL path / search params；
- 由 API 返回并可重新获取的服务端状态。

只有多个页面确实需要共享同一份不可由 URL 或服务端恢复的状态时，才评估全局状态方案。

表单要求：

- 页面表单状态与 API DTO 分离；
- schema 驱动字段仍需前端进行基础可用性校验，但后端校验是最终权威；
- 提交期间防止重复提交；
- 服务端错误不得被通用“网络错误”覆盖；
- 日期、数字、枚举和可空值转换必须显式。

### 9. 加载、空态与错误态

每个真实数据页面都应明确处理：

- 初始加载；
- 局部刷新；
- 空结果；
- 权限或未登录；
- 参数校验失败；
- 任务运行中、成功和失败；
- 资源不存在或不属于当前用户；
- 后端不可用。

不要用 mock 数据、旧缓存或硬编码样例掩盖真实空态和失败态。

### 10. 重构规则

重构必须小步进行，不一次性重写整个页面或 feature。

推荐顺序：

1. 抽纯函数；
2. 抽展示组件；
3. 抽业务组件；
4. 抽 hooks；
5. 最后处理图表、表格和复杂副作用；
6. 必要时再拆分路由级代码和 bundle。

每次重构必须满足：

- 页面行为不变，除非任务明确改变；
- API 协议不变，或变更被显式同步；
- UI 风格不被顺手改动；
- 不引入无关依赖；
- 改动范围可解释、可回滚；
- mock 与 HTTP 两条 adapter 路径不被无意破坏。

阶段性“最高优先级页面”不写入本文件，应放入 issue、roadmap 或任务文档。本文件只保留长期规则。

### 11. 性能与构建

- 避免在 render 中重复进行大规模转换、排序或 JSON 解析；
- 对大图表、大表格和独立页面优先评估延迟加载；
- 不因消除构建 warning 一次性重构全部前端；
- bundle 拆分应按真实页面和业务边界推进，不制造过度碎片；
- 新依赖必须说明用途，避免引入与现有能力重复的大型库。

### 12. 验收要求

前端运行逻辑修改完成后至少运行：

```bash
npm run build
```

如果项目配置了 lint 或 test，也应运行对应命令。纯文档任务经明确授权可以不运行构建或测试，但交付说明必须如实记录。

提交说明需要写清：

- 修改了哪个 page / feature / api adapter；
- 拆出了哪些 components / hooks / lib；
- 是否改变业务行为或 API 协议；
- 真实 HTTP 与 mock 模式的影响；
- 验证命令、结果和未运行项。
