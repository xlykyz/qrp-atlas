# 项目蓝图标准启动

## 核心目标

把模糊的“开始做项目”转换为一套获得批准、可以执行、可以验收、可以控制变更的项目基线。

始终遵守以下顺序：

```text
真实现状审计
→ 项目授权与价值定义
→ 完整产品终点
→ 范围与明确排除项
→ 需求与可追踪性
→ 架构和模块边界
→ WBS 与工作包
→ 依赖和路线图
→ 验收与质量门禁
→ 范围基线批准
→ 才允许进入实现
```

不要把“先做一个最小版本看看”默认当作项目终点。允许分阶段交付，但必须先定义完整终点、阶段边界和中间版本不包含什么。

## 开始前读取

1. 读取仓库根目录与相关子目录的 `AGENTS.md`、`README`、架构文档、已有蓝图、路线图、任务文档和发布验收报告。
2. 审计真实代码、测试、数据库契约、API、前端、部署和最近 PR；不得仅依据过期文档判断现状。
3. 判断项目类型：
   - `GREENFIELD`：全新产品或仓库；
   - `BROWNFIELD`：既有产品重大扩建；
   - `VERSION`：既有产品的新版本；
   - `RECOVERY`：范围漂移、长期未完成或需要重新封版。
4. 需要 PMP/PMI 术语、蓝图目录模板或 QRP 实践经验时，读取：
   - [PMI/PMP 实践映射](references/pmi-practice-map.md)
   - [蓝图文档模板](references/blueprint-templates.md)
   - [QRP 两次蓝图实践经验](references/qrp-lessons.md)
   - [蓝图质量与发布门禁](references/quality-gates.md)

## 输入不足时的处理

只询问会实质改变范围基线的问题。优先从仓库、现有文档、历史 PR 和用户已给信息中求解，不重复提问。

至少需要明确：

- 项目或版本名称；
- 要解决的问题和预期价值；
- 当前真实基线；
- 最终用户或使用者；
- 决策者和验收人；
- 硬约束；
- 目标版本或阶段；
- 是否允许新增顶级模块、外部依赖或高风险生产能力。

无法确认的事项进入“待决策清单”，不得伪装成已确定事实。

## 第一步：建立当前能力审计

输出事实，不输出愿景。

审计至少覆盖：

- 仓库、分支、基线 commit 和未合并 PR；
- 现有用户路径和真实可运行闭环；
- 数据、契约、指标、业务逻辑、执行、结果、API、前端、运维；
- 已完成、部分完成、仅有文档、未实现、已废弃；
- 兼容接口、技术债和旧语义；
- 测试数量、验收证据和已知边界；
- 文档与代码不一致处。

使用统一状态：

```text
✅ 已完成
🟡 部分完成
⚪ 契约或文档已有
⛔ 未实现
🧊 已冻结/兼容保留
🗄 LEGACY
➡ 后续版本
```

每个结论尽量附代码路径、测试、PR、commit 或运行证据。

## 第二步：建立轻量项目章程

章程用于正式回答“为什么做、谁批准、做到什么程度”。

至少定义：

- 背景与问题；
- 预期价值和成功结果；
- 项目类型与版本；
- Sponsor、Product Owner、Project Manager、最终验收人；
- 高层范围；
- 高层排除项；
- 关键约束与假设；
- 重大风险；
- 里程碑；
- 启动和暂停条件；
- 授权语义。

个人项目允许一人兼任多个角色，但仍要显式记录决策权和验收权。

## 第三步：冻结完整产品终点

以最终用户路径描述产品，而不是以模块目录描述产品。

产品终点必须包含：

- 最终使用流程；
- 每日、每次或每周期的标准输入和输出；
- 必须具备的能力；
- 性能、可靠性、安全、审计和可恢复性；
- 正式生产范围；
- 明确增强项；
- 明确排除项；
- 发布阻塞条件；
- 最终演示场景。

区分：

```text
完整终点：项目最终必须达到的能力
阶段交付：按依赖拆分后的可验收增量
MVP：仅在用户明确批准时存在
原型：验证交互或技术，不代表生产完成
```

禁止用中间阶段替换完整终点。

## 第四步：建立需求与追踪矩阵

给每项正式需求稳定编号，例如：

```text
REQ-DATA-001
REQ-STRATEGY-003
REQ-LIVE-007
NFR-RECOVERY-002
```

每项需求至少关联：

- 来源；
- 业务价值；
- 优先级；
- 所属范围；
- 工作包；
- 设计或契约；
- 实现路径；
- 测试；
- 验收证据；
- 状态；
- 变更记录。

要求形成：

```text
需求 → 工作包 → 代码/配置 → 测试 → 验收证据
```

无法追踪的需求不得标记完成。

## 第五步：冻结架构和模块边界

先复用现有地基，再决定扩建。

必须明确：

- 现有架构是否继续封版；
- 允许新增哪些顶级模块；
- 各模块负责什么；
- 各模块明确不负责什么；
- 依赖方向；
- 数据所有权；
- 运行时编排；
- 回测、模拟和生产是否共享语义；
- 旧接口的兼容或废弃策略；
- 外部系统适配边界。

禁止：

- 为单一功能随意新增顶级模块；
- 在事实/指标层输出业务动作；
- 在策略层访问数据库或外部执行 SDK；
- 在执行层硬编码具体策略逻辑；
- 为赶进度复制已有能力；
- 在未定义迁移方案时原地改写稳定版本。

## 第六步：创建 WBS 和工作包

WBS 必须以交付物为导向，覆盖批准范围的 100%。

先定义阶段和工作包，再定义活动。不要把零散编码动作直接当成 WBS 顶层。

每个工作包必须包含：

- 编号和名称；
- 目标；
- 业务价值；
- 前置条件；
- 正式范围；
- 明确不做；
- 输入；
- 输出；
- 数据/接口/版本语义；
- 受影响模块；
- 迁移和兼容；
- 测试矩阵；
- 验收标准；
- 失败与回滚；
- 分支与 PR 约束；
- 完成后的文档同步；
- 独立退出条件。

工作包应足够小，可以独立估算、分派、开发、评审和验收；又应足够完整，能够形成真实交付物。

## 第七步：建立路线图和依赖

路线图首先表达逻辑依赖，不虚构日期。

输出：

- 阶段顺序；
- 工作包依赖；
- 可并行与必须串行项；
- 关键路径候选；
- 每阶段入口和退出条件；
- 里程碑；
- 外部依赖；
- 暂停点和人工授权点。

只有在已有工作量估算、资源和日历时，才建立正式进度基线。否则明确标注为“逻辑路线图，不是承诺日期”。

默认规则：

- 蓝图和范围基线先于运行代码；
- 数据与契约先于计算和策略；
- 客观事实先于决策；
- 回测验证先于生产执行；
- 中立核心先于具体供应商适配；
- 生产监控、恢复和审计属于正式范围，不是收尾附加项。

## 第八步：建立质量、风险和验收门禁

至少建立：

- 功能验收；
- 架构边界；
- 数据质量和时间语义；
- 安全；
- 权限与 owner 隔离；
- 性能；
- 可复现；
- 兼容；
- 迁移；
- 异常路径；
- 恢复；
- 运维；
- 文档；
- 全量测试和构建；
- 真实演示场景。

风险登记至少包含：

```text
risk_id
description
probability
impact
trigger
owner
response
contingency
status
```

高风险能力必须定义分阶段授权，例如：

```text
离线验证 → 纸面模拟 → 仿真环境 → 小范围生产 → 扩大授权
```

## 第九步：建立范围和变更控制

蓝图批准后，将以下内容视为范围基线：

```text
产品范围说明
+ WBS
+ 工作包定义
+ 验收基线
```

把后续变化分类为：

- `DEFECT`：实现不符合已批准基线；
- `CLARIFICATION`：不改变能力和验收的澄清；
- `PARAMETER_CHANGE`：只改变参数版本；
- `RULE_VERSION_CHANGE`：改变业务行为，必须创建新版本；
- `SCOPE_CHANGE`：改变交付能力、工作包或发布门禁；
- `RESEARCH_HYPOTHESIS`：待验证想法；
- `BACKLOG`：后续版本候选。

任何 `SCOPE_CHANGE` 必须记录：

- 变更原因；
- 受影响需求；
- 受影响工作包；
- 架构、进度、成本、风险和测试影响；
- 兼容和迁移；
- 批准人；
- 批准日期；
- 基线版本。

研究结果只能生成变更提案，不得自动修改生产规则、参数、事实库或执行计划。

## 第十步：生成蓝图成果包

默认输出到：

```text
docs/<项目或产品>产品蓝图<版本>/
```

使用 [蓝图文档模板](references/blueprint-templates.md) 的目录。根据项目规模裁剪文档数量，但不得删除以下逻辑成果：

- 当前能力审计；
- 项目章程或启动决策；
- 完整产品终点；
- 范围和排除项；
- 需求追踪；
- 架构与模块边界；
- WBS 与工作包；
- 路线图和依赖；
- 验收；
- 风险；
- 变更控制。

## Git 和 PR 规则

蓝图应使用独立分支和独立 PR。

要求：

- 从最新目标分支创建；
- 蓝图 PR 默认 docs/skill-only；
- 不提前修改运行代码；
- PR 描述列出基线 commit、文件范围、文档数量和未运行的测试；
- 明确“合并蓝图不等于功能完成”；
- PR 保持未合并，等待审查；
- 蓝图批准后才拆开发工作包；
- 每个工作包独立 PR，禁止顺手扩展范围。

## 最终回复格式

汇报：

1. 项目类型与审计基线；
2. 蓝图目录和核心范围决定；
3. WBS/工作包数量与主依赖；
4. 仍待决策事项；
5. Git 分支、commit、PR 和验证；
6. 合并语义；
7. 下一步只指向第一个已批准工作包。

不要重复长篇复述所有文档内容。

## 完成前自检

逐项检查 [蓝图质量与发布门禁](references/quality-gates.md)。

以下任一情况存在时，不得宣告蓝图封版：

- 产品终点仍是模糊愿景；
- 现状审计没有代码或运行证据；
- 范围没有明确排除项；
- 工作包之间重叠或遗漏；
- 验收标准不可测试；
- 需求无法追踪到测试；
- 进度日期缺少估算基础；
- 高风险能力没有分级授权；
- 旧版本和兼容策略未定义；
- 变更控制无法阻止边做边改；
- 合并语义与功能完成混淆。
