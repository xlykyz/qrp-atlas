# 蓝图质量与发布门禁

## A. 启动与价值

- [ ] 项目类型明确。
- [ ] 问题、价值和成功结果明确。
- [ ] Sponsor、决策者和验收人明确。
- [ ] 高层约束、假设和风险明确。
- [ ] 启动、暂停和终止条件明确。

## B. 现状审计

- [ ] 基线 branch/commit 明确。
- [ ] 未合并 PR 已审计。
- [ ] 代码、契约、测试、运行和文档均已检查。
- [ ] 文档与代码差异已列出。
- [ ] 已完成、部分完成、仅文档、未实现和 LEGACY 已区分。
- [ ] 结论有路径、测试、PR 或运行证据。

## C. 产品终点

- [ ] 终点以用户路径描述。
- [ ] 标准输入和输出明确。
- [ ] 必须能力、增强项和排除项明确。
- [ ] 非功能要求明确。
- [ ] 发布阻塞条件可验证。
- [ ] 中间阶段没有替换完整终点。
- [ ] 最终演示场景覆盖核心价值。

## D. 需求

- [ ] 正式需求有稳定 ID。
- [ ] 每项需求有来源和价值。
- [ ] 需求关联工作包。
- [ ] 需求关联实现和测试。
- [ ] 需求关联验收证据。
- [ ] 非功能需求未遗漏。
- [ ] 无法确定事项进入待决策清单。

## E. 架构与边界

- [ ] 现有地基和复用策略明确。
- [ ] 顶级模块变化经过授权。
- [ ] 每个模块的负责与不负责明确。
- [ ] 依赖方向明确。
- [ ] 数据所有权明确。
- [ ] 外部系统通过适配边界接入。
- [ ] 回测、模拟和生产语义关系明确。
- [ ] 旧接口兼容和迁移策略明确。
- [ ] 没有明显重复实现或循环依赖。

## F. WBS 和工作包

- [ ] WBS 面向交付物。
- [ ] WBS 覆盖批准范围的 100%。
- [ ] 同层范围无重复。
- [ ] 测试、迁移、文档、运维和发布工作已纳入。
- [ ] 每个工作包可独立估算、分派和验收。
- [ ] 每个工作包有前置、输入、输出和退出条件。
- [ ] 每个工作包有“明确不做”。
- [ ] 每个工作包有测试矩阵和失败路径。
- [ ] 工作包名称与需求和路线图一致。

## G. 路线图与进度

- [ ] 逻辑依赖明确。
- [ ] 串行和并行规则明确。
- [ ] 里程碑和人工授权点明确。
- [ ] 外部依赖明确。
- [ ] 未经估算的日期没有伪装成进度承诺。
- [ ] 关键路径候选已识别。
- [ ] 高风险能力采用分级授权。

## H. 验收与质量

- [ ] 功能验收明确。
- [ ] 架构边界可检查。
- [ ] 数据质量和时间语义可测试。
- [ ] 安全和权限可验证。
- [ ] 性能和容量目标明确。
- [ ] 可复现和审计目标明确。
- [ ] 兼容、迁移和回滚可验证。
- [ ] 异常、重启和恢复场景明确。
- [ ] 全量测试、构建和静态检查明确。
- [ ] 正式演示可重复。

## I. 风险与变更

- [ ] 风险有概率、影响、触发器、责任人和响应。
- [ ] 范围基线组成明确。
- [ ] 变更类型明确。
- [ ] 参数、规则版本和范围变化已区分。
- [ ] 范围变更需要影响分析和批准。
- [ ] 研究假设不能自动改变生产规则。
- [ ] 紧急变更和事后审计机制明确。
- [ ] 基线版本和变更日志明确。

## J. Git 与交付

- [ ] 蓝图使用独立分支和 PR。
- [ ] 蓝图 PR 未混入运行代码。
- [ ] 起始 main 和当前 head 明确。
- [ ] changed files 与目录索引一致。
- [ ] 未运行测试的原因诚实说明。
- [ ] PR 明确“合并不等于功能完成”。
- [ ] PR 保持未合并等待审查。
- [ ] 下一步只进入第一个已批准工作包。

## 否决条件

存在以下任一项时，不得批准蓝图：

- 只列功能愿望，没有范围边界；
- 只列开发任务，没有产品终点；
- 只列模块，没有用户闭环；
- 只列 Happy Path，没有失败、恢复和运维；
- 工作包无法独立验收；
- 需求和测试无法追踪；
- 高风险自动化没有权限和分级授权；
- 新增顶级模块没有理由；
- 使用“先做最小版再说”回避完整目标；
- 未建立变更控制，预计边做边改；
- 蓝图文档与仓库真实状态明显不一致。
