# QRP 两次蓝图实践经验

## 适用目的

这些经验用于校正 Agent 在软件和交易系统项目启动中的常见偏差，不要求新项目复制 QRP 的具体模块。

## 实践一：QRP 产品蓝图 v1.0

### 有效做法

- 先审计现有架构、代码和测试，再定义产品终点。
- 以稳定模块边界约束能力扩建，避免产品建设演变为架构重写。
- 用代表性能力覆盖，而不是把全部学术和远期能力都列为发布门禁。
- 将总控文档与逐任务文档分离：产品终点、模块规划、路线图、任务包、总体验收各司其职。
- 每个任务形成独立 PR、测试证据和验收结论。
- 最终用真实产品链、权限隔离、结果比较、重放和完整构建完成发布级验收。

### 暴露的问题

- 蓝图文档会随着代码推进变旧，需要任务 00 持续校准。
- “研究能力已存在”不等于“产品入口已完成”。
- “后端验收完成”不等于“正式发布完成”或“产品已经好用”。
- 增强项和正式门禁必须持续区分，否则容易无限扩张。

## 实践二：QRP 产品蓝图 v1.1

### 用户关键校正

最初方案试图先做 System B 的最小状态机，再逐步扩展。用户明确否决：

> 不要最小，要完整能力；先模块化拆解工作包，再逐步实现；不要边干边改目标和边界。

由此形成以下原则：

- 先一次性定义完整终点，阶段交付不能替换终点。
- 先冻结生产范围、LEGACY、排除项和兼容策略。
- 先建立全部工作包的输入、输出、边界和验收，再开始代码。
- 增加专门的“范围基线与变更控制”文档。
- 把中立业务核心与外部供应商适配分离，避免具体 SDK 污染上层语义。
- 蓝图 PR 只批准范围与 WBS，不代表任何运行能力已经完成。

## 两次实践共同结论

### 1. 现状审计必须基于真实仓库

不要根据记忆写“当前能力”。读取代码、测试、最新 main、未合并 PR、发布验收和运行结果。

### 2. 目标、架构、范围和计划是不同工件

- 产品终点回答“最后能做什么”；
- 架构回答“能力放在哪里”；
- 范围回答“这个版本做什么和不做什么”；
- WBS 回答“交付物如何分解”；
- 路线图回答“按什么依赖顺序完成”；
- 验收回答“怎样证明完成”。

不要把它们挤在一份模糊计划里。

### 3. 工作包要形成真实闭环

仅增加数据表、指标函数或页面，不一定构成完整工作包。工作包应有可验证交付物和独立退出条件。

### 4. 兼容性要在蓝图阶段决定

稳定接口不得在实现时临时决定是否破坏。应提前选择：

- 原地升级；
- 新版本并存；
- 适配器；
- 数据迁移；
- LEGACY；
- 正式废弃。

### 5. Agent 需要更强的范围约束

常见漂移包括：

- 顺手重构；
- 增加新模块；
- 用新想法插入当前工作包；
- 把研究结论直接写入生产规则；
- 用少量通过测试宣告产品完成；
- 把暂时可运行当成发布就绪。

因此每个工作包必须有“明确不做”，PR 必须对应单一批准范围。

### 6. 文档状态也需要配置管理

蓝图是受控交付物。应记录：

- 基线 commit；
- 文档版本；
- 批准状态；
- 关联 PR；
- 状态校准日期；
- 变更日志。

### 7. 主线默认串行

当一个人的注意力、多个 Agent 和多个工作站共同参与时，并行会放大上下文切换和集成风险。除非依赖清晰且用户明确授权，否则主线工作包串行推进。

## 新项目应用方式

启动新项目时，不复制 QRP 的工作包名称，而复用以下机制：

```text
真实能力审计
+ 完整产品终点
+ 模块边界
+ 范围基线
+ WBS 字典式工作包
+ 独立 PR 和验收
+ 变更控制
```
